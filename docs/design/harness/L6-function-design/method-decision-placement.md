# 方式の決定の置き場 - 機能設計 (Issue #1923)

## 1. 目的と範囲

consumer (UT-TDD を導入した先の製品開発) の V-model 文書で、**後から変えにくい方式の選択** (データの保存方式、テナント分離、認証方式など) をどこに正本として置くかを決める。

実測 (#1923): 配布テンプレートは、選ぶ前に答えが書いてある。L3 は「全業務エンティティは tenant_id を必須保持する」、L5 は「全テーブルに tenant_id 先頭のインデックス、RLS で分離」と固定している。データの保存方式を選ぶ節も、テナント分離を選ぶ節も無い。AI の worker は例文をそのまま埋めるので、単一組織のシステムにも tenant_id と RLS が「検討した結果」として入る。

#1927 のゴール (要件と UI が確定したら、人の判断待ちで止まらずに受入まで進む) を満たすには、方式が **選択済みで、承認済みで、後続の文書がそれを読める** 必要がある。選択肢を並べるだけでは、後続は選べずに止まるか、AI が黙って選ぶ。

範囲外:

- DoR (#1928) の検査項目・署名の形式・警告モードから fail-close への移行。本書は DoR が読む範囲だけを定める (§7)。
- テンプレート本体の改訂 (#1930)。本書の freeze の後に、テンプレートを本書へ合わせる (§8)。
- 個々の方式 (RDB か KVS かなど) の優劣。本書は置き場と記録の形を定め、方式の中身は決めない。

## 2. 用語 (各語の定義はここだけに置く)

| 語 | 定義 |
|---|---|
| 方式の決定 | 後から変えにくい方式の選択。変えると L4 / L5 の複数文書とデータの移行が要るものを指す。 |
| 論点 | 方式の決定の対象 1 件 (例: データの保存方式)。論点 ID は小文字 ASCII の kebab-case とする。 |
| 必須論点 | すべての consumer が決定記録を持つ論点。`data-store` (データの保存方式)、`tenant-isolation` (テナント分離)、`authn` (認証方式) の 3 種。 |
| 決定記録 | 論点 1 件につき 1 件、L3 の「方式の決定」章に置く記録。記録 ID は `DEC-NNN` (3 桁の連番)。書式は §3.4。 |
| 選んだ方式 | 決定記録の欄。採用した方式を 1 つだけ、方式コードと日本語の説明の組で書く。方式コードは小文字 ASCII の kebab-case (例: `db-per-tenant`、`shared-schema-rls`、`none-single-org`)。「分離なし (単一組織)」のような「その論点が要らない」という選択も選んだ方式である。欄の値は `<方式コード>: <説明>` の形で、最初の `: ` より前を方式コードとして読む。 |
| 却下した案 | 決定記録の欄。比較して採らなかった案と、却下の理由。 |
| 承認 | PO が決定記録を認めた記録。§5.1 の 4 項目で成り立つ。 |
| 詳細 | 選んだ方式を実現する設計 (スキーマ、物理配置、認証フローなど)。L4 / L5 に置く。決定ではない。 |
| 適用条件 | 項目が、特定の論点の方式コードに応じて必須になることを示す注記。形は `適用条件: <論点 ID>=<方式コード>` または `適用条件: <論点 ID>!=<方式コード>` で、論点 ID と方式コードは小文字 ASCII の kebab-case (英小文字と数字の語を `-` でつないだもの)。条件の終わりと、条件が掛かる項目の範囲は、表の直後の「適用条件の範囲」で定める。`=` は「その論点の承認済みの決定記録の方式コードが一致するとき」、`!=` は「一致しないとき」に限り適用される。承認済みの決定記録が無い論点の条件は評価しない (適用・非適用のどちらにも判定せず、§6.3 の矛盾にも数えない)。この書式に合わない `適用条件:` は `applicability_condition_invalid` (§6.3、§8)。 |
| 非適用 | 適用条件が、承認済みの決定記録の方式コードにより適用されない項目の状態。必須として扱わない。 |
| 予約語 | 論点 `tenant-isolation` の方式コードのうち、`none-single-org` は「分離なし」、`row-level` は「行レベル分離 (共有の DB・schema で、行ごとにテナントを分ける方式)」を意味する予約語であり、分離しない選択は `none-single-org`、行レベル分離を選ぶ選択は `row-level` で書く。予約語は、テンプレートが適用条件を書くための語彙であり、決定を先に埋めるものではない (どの consumer にも、予約語を選ぶことを求めない。選んだ方式の値は限定しない、§10)。予約語以外の方式コードは consumer が決める。`shared-schema-rls` のような他の綴りは consumer 自身のコードであり、`row-level` とは別の値として読む (`=` と `!=` は方式コードの文字列の一致だけで判定し、意味の近さは読まない)。他の論点では、どちらの語も特別な意味を持たない。マルチテナントを採用した場合は `tenant-isolation!=none-single-org`、行レベル分離のときだけ掛かる項目は `tenant-isolation=row-level` と書く。 |
| 参照行 | L4 / L5 が決定記録を参照する 1 行。形は `参照する決定記録: DEC-NNN (論点 ID: <論点 ID>)`。 |
| 論点 ID の表記 | 見出しと参照行で、論点 ID はバッククォート 1 組で囲んでも囲まなくてもよい。同じ値として読む。 |
| 方式決定の検査 | 本書の判定 `judgeDecisionRecords`、`judgeApprovedBaseline`、`judgeDetailDocs`、`judgeTemplateItems` を行う検査の総称。DoR (#1928) は、このうち Git を読まない `judgeDecisionRecords` の結果だけを使う (§7)。 |

**適用条件の範囲** (§2 の適用条件の一部。1 つの入力に読み方が 1 つだけになるよう、始まり・終わり・掛かる範囲を定める)

- 始まり: `適用条件:` (半角コロン) の直後。直後の半角スペース 0 個以上は読み飛ばす。
- 終わり: 始まりの位置から、文法 `<論点 ID>=<方式コード>` または `<論点 ID>!=<方式コード>` に合う最長の並びまでが条件である。その次の文字 (空白、句読点、「のとき」などの続き) で条件は終わり、続きは条件に含めない。続きに別の `<論点 ID>=<方式コード>` が書いてあっても条件ではなく、複数の条件を束ねる書き方 (かつ / または) は無い。例外として、最長の並びの次の文字が ASCII の英数字、`_`、`-`、`=`、`!` のとき (`tenant-isolation=db_per_tenant` が `db` で切れる場合など) は、条件が途中で切れているので書式に合わない。文法に合う並びが 1 つも取れないときも書式に合わない。書式に合わない `適用条件:` は `applicability_condition_invalid` である。
- 掛かる範囲: その `適用条件:` を含む 1 項目だけである。項目は、箇条書きの 1 項目 (継続行を含む。入れ子の子の項目は別の項目)、表の 1 行 (セルをまたいで 1 項目)、段落 1 つ (空行で区切られた連続行。引用 `>` は記号を除いて読む) のいずれかである。隣の項目、親・子の項目、同じ表の他の行、直前や直後の段落には及ばない。
- 1 つの項目に `適用条件:` が 2 つ以上あるときは、その項目は `applicability_condition_invalid` とする (どの条件も評価しない)。この reason が抑える集合と併発する reason は §6.3 のとおりである。

## 3. 置き場 (二段)

**3.1 L3 に決定記録を置く**

置き場は `DOC-L3-FUNCTIONAL` (要件定義書) の **第9章「方式の決定」** とする。既存の章番号は動かさない (第8章 未確定事項の後ろに足す)。決定記録は論点ごとに 1 件、第9章にだけ置く。

- 方式の決定を L0、L1、L2、L4、L5 に置かない。L0 の代替案の比較 (事業としての採否) は方式の決定ではなく、本書の対象外である。
- 必須論点を第8章 (未確定事項) へ書くだけで済ませない。必須論点は第9章に決定記録を持つ (§4.2)。

**3.2 L4 / L5 に詳細を置く**

詳細は L4 / L5 の該当文書 (例: `DOC-L4-DATA`、`DOC-L4-SECURITY`、`DOC-L5-PHYSICAL-DATA`) に置き、どの決定記録の詳細かを `DEC-NNN` で参照する (§6)。L4 / L5 は決定記録の「選んだ方式」「理由」「却下した案」を持たない。

**3.3 ADR との関係**

決定記録は、ADR を 1 件参照する (`ADR 参照` 欄)。ADR は既存の運用 (consumer の `docs/adr/`、テンプレート optional 014 の第3章 ADR 一覧) をそのまま使い、新しい ADR の様式を作らない。

| 持つもの | 置き場 |
|---|---|
| 選んだ方式、理由の要約、却下した案と却下の理由 (各 1〜2 文)、承認 | L3 の決定記録 (正本) |
| 背景、比較の根拠 (計測・制約の引用)、決定の履歴 | ADR |

ADR の「決定」は、決定記録の「選んだ方式」と同じ内容でなければならない (食い違うときは、ADR を直して再度承認を受ける。これは非著者 review で確かめ、機械では検査しない)。承認の正本は決定記録の承認欄であり、承認済みの記録が参照する ADR の status は `accepted` でなければならない (§4.1 の欄 7)。

**3.4 決定記録の書式**

第9章の中の見出しは、論点ごとに 1 つの `##### 9-N <日本語名> (論点 ID: <論点 ID>)` とする (N は数字、論点 ID の表記は §2)。決定記録はその見出しの下に置く表で、1 件につき 1 つの 2 列の表 (欄名 | 値) とする。表の 1 行目は見出し行 (列名は読まない)。`DEC-NNN` を表題として持つ位置は、欄名が `記録 ID` の行の値である。2 行目以降の欄名は §4.1 の 10 欄である。値の読み方は次のとおり。

- 承認の値は `承認者: <値> / 承認日: <値> / 承認対象 revision: <値> / 承認根拠: <値>` の形で、項目名の後の値が空、または項目名が無いとき、その項目は欠ける (§5.1)。
- 起草の値は `<起草者> / AI の推奨: <方式コード>` の形で読む。

**未記入 (プレースホルダ)**: 値が `<` と `>` で囲んだ部分 (`<` の後に `<` と `>` 以外の文字が 1 字以上続き、`>` で閉じるもの) を 1 つ以上含むとき、その値は未記入である (例: `DEC-<NNN>`、`<方式コード…>`)。未記入の値を 1 つでも持つ表は、次の 1〜4 より先に、決定記録として数えない表にする。この表は `decision_markup_invalid` を出さない (同じ表が 1〜4 の違反を併せ持っていても出さない)。また §4.1 の欄の規則の対象にもならない (記録が無いのと同じ扱い)。結果は入力の種類で決まる。

- consumer の文書の第9章: 数えない表になり、その論点は記録が 0 件の論点として §4.2 の `required_topic_missing:<論点 ID>` で判定される (`decision_field_missing` は出さない)。表が属する見出しの論点が必須論点でなければ、reason は出ない。
- 配布テンプレートの第9章 (空の様式、§8.4): どの reason も出さない。テンプレートには `judgeDecisionRecords` を適用せず、必須論点の記録が 0 件でも不適合にしない。
- 見出しは値ではないので、見出しの `<…>` は本規則の対象外であり、`decision_markup_invalid:heading` のままである (下記)。

表は、次の順に調べて最初に当たった 1 種別だけの `decision_markup_invalid:<種別>` を出し、決定記録として数えない (他の規則の対象にしない)。

1. `table_shape`: 見出し行を除く行に、セルが 2 つでない行がある。
2. `record_id`: `記録 ID` の行が無い、または値が `DEC-` と 3 桁の数字の形でない。
3. `topic_mismatch`: `論点` の欄の値が、表が属する見出しの論点 ID と違う。
4. `record_id_duplicate`: 1〜3 を通った表の間で、記録 ID が他の表と同じ (同じ記録 ID の表はすべて数えない)。

第9章の `##### 9-` で始まる見出しが上の形に合わなければ `decision_markup_invalid:heading` を出し、その見出しの下の表は決定記録として数えない。見出しの下に無い表 (第9章の冒頭の注記など) は決定記録でなく、reason も出さない。数えない表だけの論点は、記録が 0 件の論点として §4.2 で判定される。

## 4. 決定記録の必須項目

### 4.1 欄と規則

決定記録は次の欄をすべて持つ。

**空欄の規則 (全欄に共通):**

- 「欠ける」は、欄が無い、または値が空 (空文字、空の一覧) のことである。
- 欄 1・2・3・5・7・8・9・10 は、状態 (欄 9) を問わず、欠けたら `decision_field_missing:<欄名>` とする。
- 欄 4 (却下した案) の「案が 0 件」と、欄 6 (承認) の欠落は、`decision_field_missing` を出さず、下表の専用の reason だけを出す。欄 4 の「案はあるが却下の理由が空」は `decision_field_missing:却下した案` を出す。
- 欄 7 (ADR 参照) は、欄が無いか空なら `decision_field_missing:ADR 参照` だけを出す。path があるが ADR が存在しない、または status が合わないときは `adr_ref_invalid` だけを出す。
- 状態が `proposed` の記録は、欄 6 の 4 項目が空でよい (承認前の起草を許す明示の例外)。`superseded` の記録は、承認 4 項目を持っていた場合それを残す (消さない)。
- 複数の規則が同時に当たるときは、当たった reason をすべて出す。ある規則が別の規則を打ち消すことはない (専用の規則を持つ欄が、一般の規則と二重に出ることもない)。承認対象 revision (欄 6) が空の `approved` の記録は `judgeDecisionRecords` が `approval_incomplete` を出し、`judgeApprovedBaseline` (§4.3) は照合しないので `approval_baseline_unavailable` は出ない。

| 欄 | 内容 |
|---|---|
| 1. 論点 | 論点 ID。 |
| 2. 選んだ方式 | 方式コードと説明を 1 つ。 |
| 3. 理由 | この要件・制約にどう合うか (要件 ID か制約を 1 つ以上引く)。 |
| 4. 却下した案 | 1 案以上。各案に却下の理由。選んだ方式と却下した案を合わせて 2 案以上が比較されていること。案が 0 件 (欄が無い、または空の一覧) なら `decision_alternatives_insufficient` だけを出す。案が 1 件以上あり、いずれかの案の却下の理由が空なら `decision_field_missing:却下した案` を出す。 |
| 5. 起草 | 起草者 (AI の場合はモデル名)。AI が推奨した方式コードを併記する。AI の推奨と選んだ方式が違うときは、PO の判断理由が欄 3 に書かれていること。 |
| 6. 承認 | §5.1。状態が `approved` のときは 4 項目すべてが必須で、1 つでも欠ければ `approval_incomplete` だけを出す (`decision_field_missing` は出さない)。状態が `proposed` のときは空でよい。 |
| 7. ADR 参照 | consumer の `docs/adr/` の ADR への path。その ADR が存在すること。状態が `approved` の記録では、その ADR の status が `accepted` であること。満たさなければ `adr_ref_invalid`。状態が `proposed` の間は、ADR が存在すれば status は問わない。 |
| 8. 詳細の置き場 | 詳細を書く予定の L4 / L5 文書 ID (`DOC-L4-DATA` など) を 1 つ以上。予定であり、存在は検査しない (§7)。 |
| 9. 状態 | `proposed` / `approved` / `superseded` のどれか。 |
| 10. 置換元 | この記録が置き換える旧 `DEC-NNN`。置換でなければ `-`。 |

### 4.2 必須論点

第9章は `data-store`、`tenant-isolation`、`authn` の 3 論点のそれぞれに、`superseded` でない決定記録をちょうど 1 件持つ。0 件なら `required_topic_missing:<論点 ID>`、2 件以上なら `decision_duplicate:<論点 ID>`。必須論点は、選んだ方式の値を限定しない。「分離なし」「外部 IdP に委譲」のように、その論点が要らない・自前で持たないという選択も、記録があれば適合である。

必須論点以外の論点 (ファイルストレージ、検索基盤など) は、方式の決定の定義 (§2) に当たるものを consumer が足す。足した論点も本書の規則に従う。

### 4.3 変更 (置換)

`approved` の決定記録の欄 2〜4 を、その記録の中で書き換えない。判定は **比較基準** との照合で行い、これは方式決定の検査 (`judgeApprovedBaseline`) が受け持つ。**DoR は Git を読まず、この照合をしない** (§7)。比較基準は、その記録の `承認対象 revision` (欄 6) の commit にある L3 第9章の、同じ `DEC-NNN` の記録の欄 2〜4 である (consumer の既存の Git 履歴から読み、新しい保管方式は作らない)。

この照合は、状態が `approved` で `承認対象 revision` が非空の記録だけを対象にする。空の記録は `judgeDecisionRecords` の `approval_incomplete` (§5.1) だけで、`judgeApprovedBaseline` は何も出さない (二重に出さない、§4.1)。

- 現行の欄 2〜4 が比較基準と食い違う: `approved_decision_edited_in_place`。
- 非空の承認対象 revision を Git 履歴で解決できない、またはその commit に同じ `DEC-NNN` の記録が無い: `approval_baseline_unavailable`。
- 食い違いが無い: 適合。最初から別の方式で承認された記録と、承認の後に書き換えられた記録を区別できるのは、この比較基準があるからである。

方式を変えるときは次の手順を踏む。

1. 新しい `DEC-NNN` を起こし、置換元に旧記録を書く。
2. 旧記録の状態を `superseded` にする (欄 2〜4 はそのまま残す)。
3. 新しい記録を §5 の承認に通す。ADR は新しい ADR を起こして旧 ADR を supersede する (accepted の ADR を in-place で反転しない)。

## 5. 承認と責任分担

### 5.1 承認の 4 項目

状態が `approved` の記録は、承認欄に次の 4 項目をすべて持つ。1 つでも欠けるなら `approval_incomplete`。

| 項目 | 内容 |
|---|---|
| 承認者 | PO の識別子。欄 5 の起草者と同じなら `approver_equals_drafter` で不適合。 |
| 承認日 | 日付。 |
| 承認対象 revision | 承認した時点の決定記録を含む文書の revision (commit の SHA)。 |
| 承認根拠 | 承認の発言の置き場への参照 (Issue / PR のコメントの URL)。新しい保管方式は作らない。 |

DoR (#1928) の署名は L0〜L3 全体に対する署名であり、本書の承認は決定記録 1 件ごとの承認である。DoR の署名は、必須論点の決定記録がすべて `approved` であることを前提に含む (§7)。

### 5.2 AI と PO の責任分担

| 担当 | することと、してはならないこと |
|---|---|
| AI | 論点を洗い出す (必須論点 3 種に、足りない論点を追加する)。論点ごとに 2 案以上の比較案を作り、案ごとに「この要件への適合」「後から変える難しさ」を書く。推奨を 1 つ付ける。決定記録を `proposed` で起草する。**承認の項目を埋めてはならない。必須論点の記録が `approved` にならないまま、AI が方式を選んで先へ進んではならない。** |
| PO | 比較案から 1 つを選ぶ、または差し戻す。承認の 4 項目の根拠 (コメント) を残す。AI の推奨と違う方式を選ぶときは、理由を伝える (AI が欄 3 に記録する)。 |

選択肢を並べるだけでは足りない。AI は比較に加えて推奨を出し、PO が承認して初めて `approved` になる。PO の判断は設計判断のエリシテーション (`docs/governance/design-decision-elicitation.md`) の形式 (前提・選択肢・trade-off・推奨 1 つ) に従って求める。

### 5.3 戻り経路

次のいずれかのとき、後続の設計・実装は進まず、段 0 (L0〜L3 と方式の決定を作る段、#1927) へ戻る。AI が方式を補って進めることは禁止する。

- 必須論点の記録が `approved` でない (§7)。
- L4 / L5 が、第9章に無い方式の選択を持つ (`decision_outside_l3`、§6.2)。
- L4 / L5 の詳細が、承認済みの方式と矛盾する (`detail_contradicts_decision`、§6.3)。

## 6. L4 / L5 との参照関係

**6.1 詳細は決定記録を参照する**

`superseded` でない決定記録 R の「詳細の置き場」欄 (§4.1 の欄 8) が文書 ID で指す L4 / L5 の文書は、R の参照行 (§2) を 1 行以上持つ。判定は**文書単位**である。「詳細の置き場」欄は文書 ID を持ち、節を指す入力が無いので、文書の中のどの節にあっても参照行は数える。参照行を詳細を書いた節に置くことは書き方の推奨であり、機械の判定の対象にしない (非著者 review が読む)。次の参照行は数えない: 記録 ID が第9章に無い、論点 ID が記録 ID の記録の論点と違う、形が §2 に合わない。R の「詳細の置き場」が指す文書で、数える参照行が 0 件なら `detail_without_decision_ref` を出す (文書と記録の組ごとに当たるが、reason の集合では 1 つ)。

参照が要る範囲は、記録の「詳細の置き場」欄が指す文書だけである。どの記録の「詳細の置き場」にも載っていない L4 / L5 の文書には、参照行を求めない。載っている文書は、参照行が 1 行以上あれば適合であり、節ごとには求めない (節の位置は判定しない)。入力として渡されなかった文書 (まだ書かれていない) は判定しない (§7)。これは L4 / L5 の側で参照行を足せば直り、段 0 へは戻らない。

**6.2 L4 / L5 は決定を持たない**

L4 / L5 が、第9章に記録の無い論点について「選んだ方式」と「理由」を持つとき、`decision_outside_l3`。その選択が要るなら、第9章に決定記録を足して承認を受けてから、詳細を書く (段 0 へ戻る、§5.3)。

**6.3 矛盾**

L4 / L5 の必須の項目が、参照する決定記録の方式コードと両立しないときは、`detail_contradicts_decision`。判定は次の 2 つで行う。

1. その項目が適用条件 (§2) を持ち、条件の論点 ID の承認済みの決定記録の方式コードにより、その条件が適用されない (`=` なら方式コードが異なる、`!=` なら同じ)。項目を書いていること自体が矛盾であり、項目を書いていないことは矛盾でない (非適用、§8)。機械で読める。条件の書式が §2 に合わないときは `applicability_condition_invalid` を出す。この reason は、適用条件を評価して出す reason だけを抑える。抑える集合は `detail_contradicts_decision` (この判定) と `unconditional_item_presumes_decision` (§8) の 2 つである。適用条件と独立な reason (`template_prefilled_decision` など) は抑えず、当たれば併せて出す (§9)。
2. その項目の記述が、選んだ方式の説明と直接反する (非著者 review が読む)。

矛盾は L4 / L5 の側の書き換えで解決しない。段 0 へ戻し (§5.3)、PO が決定記録の置換 (§4.3) か、詳細を決定記録に合わせた書き直しのどちらかを判断する。

## 7. DoR が読む範囲

DoR (#1928) が方式の決定について読むのは、**現在の L3 第9章の決定記録と、それが参照する ADR の存在・status だけ**とする。DoR は **Git を読まない**。§4.3 の履歴との照合 (承認対象 revision 時点の第9章との比較) は DoR でなく方式決定の検査 (`judgeApprovedBaseline`) が受け持つ。DoR が使うのは `judgeDecisionRecords` の結果だけである。次の 3 点を確かめる。

1. 必須論点 3 種のそれぞれに、`superseded` でない決定記録がちょうど 1 件ある (§4.2)。
2. その記録が §4.1 の欄をすべて持つ。
3. その記録の状態が `approved` で、承認の 4 項目がそろい、ADR 参照が有効である (§5.1、§4.1 の欄 7)。

満たさない論点は `decision_not_ready:<論点 ID>` とする。認可・外部 AI へのデータの境界・PII・ライセンスの 4 項目は必須論点に足さず、DoR では人の確認項目のままにする (実導入で不足が出たら必須論点の追加を別に起こす)。DoR は **L4 / L5 の詳細を読まない**。DoR を通る時点 (段 1) では L4 / L5 はまだ書かれていないため、`詳細の置き場` (欄 8) は予定を書くだけで、存在を検査しない。L4 / L5 の側の整合 (§6) は、段 2 の L4〜L6 の pair-freeze の非著者 review で確かめる。両者の範囲は重ならない。

| 検査 | 読む文書 | 時点 |
|---|---|---|
| 決定記録の存在・欄・承認 (§4、§5、§7) | 現在の L3 第9章と、参照する ADR の status (Git は読まない) | DoR (段 1) |
| 承認後の欄 2〜4 の書き換え (§4.3) | 承認対象 revision 時点の第9章 (Git) | 方式決定の検査 |
| 詳細が決定記録を参照し、矛盾しない (§6) | L4 / L5 | 方式決定の検査と pair-freeze の review (段 2) |

## 8. テンプレートへの規則 (選択を尊重する)

テンプレート (consumer へ配る `docs/templates/vmodel`) は次を守る。#1930 は本書の freeze の後にこれへ合わせる。

1. **適用条件のない必須項目は、どの方式コードでも成り立つこと。** 特定の方式を前提にする項目は、適用条件を付ける。例: DB をテナントごとに分ける選択のとき、「全テーブルが tenant_id を持つ」を、適用条件のない必須項目にしない (`unconditional_item_presumes_decision`)。
2. 適用条件が承認済みの方式コードにより適用されない項目は非適用であり、欠けていても不適合にしない。適用条件の書式は §2 のとおりで、合わない `適用条件:` を持つ項目は `applicability_condition_invalid` を出し、条件を評価する `unconditional_item_presumes_decision` は出さない (抑える集合は §6.3)。同じ項目が結論文を持てば `template_prefilled_decision` は独立に併せて出す。テンプレートは方式コードを知らないので、「マルチテナントのとき」は `tenant-isolation!=none-single-org`、「行レベル分離のときだけ」は `tenant-isolation=row-level` と書く (§2 の予約語)。
3. 方式を前提にした結論の文 (「RLS で分離する」「案C を採用する」など) を、例とも注記せずに本文へ置かない。例文を置くときは「例」と明示し、選択肢として並べる (`template_prefilled_decision`)。
   - ER 図のエンティティも対象とする。エンティティ 1 件は 1 項目であり、表なら 1 行、コードブロックの図記法ならそのエンティティの定義の範囲である。固定するのは `tenants` エンティティ (テナント分離を前提にした結論) で、その項目の中に「例」の明示か、書式に合う適用条件 (§2) のどちらかが無ければ `template_prefilled_decision` とする。同じ項目に書式に合わない `適用条件:` があるときは、書式に合う条件が無いものとして読み、「例」の明示が無ければ `applicability_condition_invalid` と `template_prefilled_decision` を併せて出す (「例」の明示があれば `applicability_condition_invalid` だけ)。直前の注記の段落に書いた適用条件は項目が違うので及ばない (§2 の範囲)。ER 図のエンティティは §8.1 の必須項目ではないので `unconditional_item_presumes_decision` は出さない。他のエンティティが方式を前提にするかは本書では固定せず、結論の文と同じく非著者 review が読む。
4. テンプレートは第9章「方式の決定」と決定記録の欄 (§4.1) を、空の様式として持つ。必須論点の 3 種の見出しは置くが、「選んだ方式」の欄は空にする。空の様式の値は `DEC-<NNN>`、`<方式コード…>` のようなプレースホルダで書いてよく、未記入として扱う (§3.4)。

## 9. 判定の定義 (oracle の入力と出力)

| 判定 | 入力 | 出力 |
|---|---|---|
| `judgeDecisionRecords` | 現在の L3 第9章 (見出しと決定記録の表)、参照 ADR の存在・status。Git は入力にしない | 適合、または reason token の集合 (`decision_markup_invalid:<種別>` (§3.4) / `decision_field_missing:<欄名>` / `decision_alternatives_insufficient` / `required_topic_missing:<論点 ID>` / `decision_duplicate:<論点 ID>` / `approval_incomplete` / `approver_equals_drafter` / `adr_ref_invalid`)。DoR は、いずれかが出た必須論点、または状態が `approved` でない必須論点を `decision_not_ready:<論点 ID>` とする (§7)。 |
| `judgeApprovedBaseline` | `judgeDecisionRecords` が数えた記録のうち `approved` で `承認対象 revision` が非空のものと、その revision 時点の第9章 (比較基準、§4.3、Git から読む) | 適合、または `approved_decision_edited_in_place` / `approval_baseline_unavailable`。DoR は呼ばない。 |
| `judgeDetailDocs` | 決定記録と、L4 / L5 の文書・節 | 適合、または `detail_without_decision_ref` / `decision_outside_l3` / `detail_contradicts_decision` / `applicability_condition_invalid`。いずれも L3 を書き換えない。`decision_outside_l3` と `detail_contradicts_decision` は段 0 へ戻す (§5.3)。 |
| `judgeTemplateItems` | テンプレートの項目 (適用条件の有無) と決定記録 | 適合、`unconditional_item_presumes_decision`、`template_prefilled_decision`、`applicability_condition_invalid`。非適用の項目の欠落は適合。 |

reason が複数当たるときは全部を出す。例外は `applicability_condition_invalid` が抑える 2 つ (§6.3) だけで、`template_prefilled_decision` などは併発する (昇順、重複なし。§4.1 の空欄の規則に従い、専用の規則を持つ欄 4・6 は `decision_field_missing` と二重に出さない)。各判定が出す reason は、その判定の行に書いたものだけで、他の判定の reason を代わりに出さない。`承認対象 revision` が空の記録は `judgeDecisionRecords` の `approval_incomplete` だけで、`judgeApprovedBaseline` は何も出さない (§4.3)。数えない表 (§3.4、未記入の値を持つ表を含む) の欄は、欄の規則 (§4.1) の対象外である。

## 10. 不変条件

- 決定記録は L3 第9章にだけ置く。同じ論点の `superseded` でない記録は 1 件だけ。
- `approved` の記録は、承認 4 項目、有効な ADR 参照 (`accepted`)、欄 1〜4・8 がそろっている。
- 選んだ方式の値は限定しない。テンプレートも DoR も、特定の方式を要求しない。
- AI は承認の項目を書かない。
