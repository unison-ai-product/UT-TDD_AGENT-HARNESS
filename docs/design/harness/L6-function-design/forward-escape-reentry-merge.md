# L6 機能設計: Forward 離脱・再合流・PR merge・PLAN Admission の補足契約

本書は PLAN-L6-83 / 84 / 85 / 86 から還流した契約のうち、`function-spec.md` の「PLAN-L6-83 駆動モデル準拠PLAN Admission契約」「PLAN-L6-83..85 Forward離脱 / GitHub関数契約」に無かったものだけを置く (既存の節は重複させない)。実装済みの範囲は `src/execution/forward-escape.ts` と `src/plan-admission/` で、それ以外は「未実装の目標契約」と明記する。

## 1. Forward 離脱コマンド (PLAN-L6-83)

- `RequestForwardEscape` の必須入力: `command_id` (冪等キー。同 payload の再送は同結果、別 payload での再利用は拒否)、origin 4 つ組 (`origin_asset_id` / `origin_revision_id` / `origin_layer` / `origin_state`)、`escape_reason`、`drive_model`、再合流先 4 つ組 (asset / revision / layer / state)、`issue_projection` (owner / repository / title / labels)。path だけを資産の正本にせず、revision は immutable な ID で持ち current への暗黙追従を禁じる。
- `drive_model` は L4 function §3.1 の 11 値が正本で、技術 `drive` (be/fe/...) とは別の値オブジェクトである。Issue 本文・Ledger event・PLAN `route_mode` の 3 面が同じ正規化値を持つまで遷移を許可しない。checkbox や自由記述の存在は選択済みの根拠にならない。
- Ledger が authoring source、GitHub Issue は外部協調用の projection である。Issue 番号を Ledger の identity にしない。E3 (durable request) までは GitHub 障害中も記録でき、E4 (remote binding 確認) 前に E5 (off-Forward 実行開始) へ進めない。緊急の Recovery / Incident もこの順序を迂回せず、GitHub 不通時は人間 escalation と安全確保だけを別 episode に記録する。
- 関数: `classifyForwardBoundary` は `inside_forward | forward_escape | invalid`、`validateForwardEscape(command, ledger)` は欠落・stale revision・不正 state/layer・未知 drive・再合流先欠落・重複 command を structured violation で返す (throw や補完をしない。origin / 再合流先は Ledger lookup で実在確認)。`projectForwardEscapeIssue` は E2 typed event だけを受理し、Ledger 発行の opaque certificate を custody port で照合できない自己申告 event を拒否する。GitHub 成功 binding は repository / body digest / 正の issue number / node ID / HTTPS URL / observed revision を全て照合し、不正応答は E4 にせず Deferred へ落とす。`reconcileIssueProjection` は外部 Issue の削除・改変・重複・別 repository 投影を finding 化する。
- 実装状況: 上記の関数は `src/execution/forward-escape.ts` に実装済み。未達 (未実装の目標契約): 通常 Forward 辺と off-Forward 辺の閉じた分類表の固定、drive_model 三面一致の PLAN 側 gate、`U-EXISSUE-001..006` (テスト設計には `U-EXISSUE-007..016` のみ実在。1〜6 相当は `CANDIDATE-U-EXISSUE-*` として test-design 側に起こした)。三面 route_mode 照合が「escape PLAN の materialization がどの E-state から可用か」を定義していない点は未解決で、上流設計の判断待ちである。実在する依存は PLAN-L6-72 の Forward FSM 遷移契約 (E-state 列の正本)。

## 2. 駆動モデル出口と ReentryCertificate (PLAN-L6-84)

ReentryCertificate の claim は origin / escape / target / drive verification (E6) / intermediate verification (E8) / issuance / decision (`eligible | rejected | stale | human_required` + rule ID) に限る (L4 data.md と同定義)。impact graph・merge simulation・post-reentry verification (E11) は certificate の claim ではなく E10/E11 段の Ledger evidence として別に append し、E12 draft PR の後段条件が certificate とは別に参照する。

- 三証拠を融合しない: E6 (駆動モデル別 oracle。PoC=仮説と反証条件、Recovery=再現 test と guard、Reverse=観測事実と上流 backfill、Refactor=外部挙動不変と構造指標)、E8 (対象 branch/revision・fixture・環境・期待 exit を固定し、失敗を消さず append)、E11 (target revision を再読込し stale なら certificate 無効化、isolated merge candidate で影響 graph が示す設計・test-design・実装・test・DB schema・CLI・workflow を検査。subject commit と後続 PR HEAD は同一)。
- certificate は `drive_run_id` / `workflow_run_id` / Issue / PLAN revision に join できなければ eligible にならない。別 revision の green、command 文字列だけの自己申告、digest なし、時刻逆転は evidence に採用しない。
- 状態列は E7→E8→E9→E10→E11→E12。`Rejected | Stale | HumanRequired` は理由・owner・next command を伴う例外 state。skip・順序逆転・同一 provider による evidence 捏造・commit 不一致は fail-close。`evaluateReentryCertificate` は pure query、`appendReentryEvidence` は command (CQS)。
- 実装状況: 未実装の目標契約 (`src/` に ReentryCertificate の reducer は無い。所有 PLAN は PLAN-L7-437 / 438 で draft)。未達 DoD: certificate schema と reducer、全 drive model の出口が Forward layer/state へ結ばれ孤児 route が 0、GitHub 障害を跨ぐ custody 不変、`U/P-REENTRY-*` (test-design 側に `CANDIDATE-` で起こした)。

## 3. draft PR・cross review・merge gate の補足 (PLAN-L6-85)

- `RequestDraftPullRequest` の必須: certificate ID/digest、source branch/HEAD、base branch/revision、Issue back-reference、origin/再合流先、drive model、test evidence digest。eligible でない certificate・stale base・dirty/unpushed HEAD・同一 certificate の別 PR は拒否する。PR は常に draft で開き、本文は Issue への `Refs` (close 可能時だけ `Closes`)・origin/target・test profile と digest・impact/backprop 結果と既知 gap・rollback route・certificate ID/digest と subject HEAD を持つ。本文は説明用 projection で、accept 判定の正本は Ledger の typed evidence である (PR body の項目語彙は `external-if.md` §10.4 の trace block が正で、ここでは拡張しない)。
- cross review: reviewer は author と別の provider family (別 model 名でも同一 provider は不可)。live wake は reviewer provider ごとの受信面へ配送し、未実装・利用不能な面は typed unavailable で停止して無関係な Claude workspace を解決しない。review は CI green 後に開始し、verdict は `PASS | PASS-WEAK | FLAG` + 反証 citation (PASS-WEAK は 3 件以上の attack trial)。FLAG 未解消・review 時刻逆転・同一 provider・review 後の HEAD 更新は accept 不可。review comment の投稿失敗時も Ledger receipt は保持するが、GitHub へ reconcile されるまで merge 不可。
- `evaluatePullRequestAcceptance` は同一 subject HEAD で次を全て満たす場合だけ `accepted`: certificate が eligible かつ fresh / draft PR の projection 一致 / required `harness-check` の run head SHA が PR HEAD と一致 / tests-before-review 順序を含む profile green / 未解消 FLAG なし / `reviewed -> accepted` evidence policy / branch protection・人間 signoff・security/PII/production escalation。accept 後は `MarkReadyForReview` → `RequestMerge` を順に append し、`MergeObserved` に main SHA・merge commit・PR number・closed Issue・CI run を記録する。merge 直前に HEAD/base/review/CI を再読込し、変化があれば accept を stale 化する。merge 後 main CI 失敗は成功を上書きせず `PostMergeRegressionDetected` を append し、新しい Recovery/Incident Issue へ route する。
- GitHub 障害耐性: mutation は outbox command として永続化し同一 idempotency key で再送。応答不明時はまず remote を query してから再作成する。exponential backoff + jitter・retry budget・`retry_after`・circuit open・manual resume を typed event で残す。不通中も local test/review packet 生成は進むが、remote CI 確認・review projection・merge は fail-close。復旧時は Ledger と GitHub snapshot を双方向 reconcile し、外部だけに存在する PR/merge/force-push を finding 化する。credential・transcript・secret は保存せず ID/digest/redacted summary だけを持つ。
- GitHub object binding と closure (Reverse backfill 済みの契約): branch・Issue・draft PR・CI・review・merge は同じ `plan_id` / PLAN revision / `project_item_id` / exact PR HEAD に束縛する。PR trace の `plan_revision` と Issue 番号は明示必須で local schedule から補完しない。repository 同期は remote snapshot を SQLite transaction 外で観測し、検証後に確定 binding 群を単一 transaction で commit する。main 以外を base とする merge に `main:*` check binding や verified closure を発行しない。完了 status や GitHub approval 表示は closure 証拠にならず、PR HEAD 上と main merge SHA 上の exact required `harness-check`・closed Issue と同期済み Project item・canonical PLAN frontmatter 由来の claim-blind/spec-blind cross-provider receipt・PR trace の両 lane 結合 digest・accepted PLAN 状態と main base custody が同じ revision/HEAD に揃うまで `merge-closure` が阻害する。closure receipt は repository 同期だけが生成し、手動観測入口から作れない。同一 PLAN の正式 revision 更新は同じ merge identity へ再収束でき、異 PLAN への再割当は拒否、stale replay は既存証拠を後退させない (物理格納は `physical-data.md` の merge closure receipt)。
- 実装状況: closure / binding は実装済み (repository 同期)。draft PR の自動生成・PR 状態機械・障害耐性 (outbox・circuit) は未実装の目標契約 (所有 PLAN は PLAN-L7-439 で draft)。未達 DoD: 上記 gate の順序付き fail-close、`U/P-PRFLOW-*` (`CANDIDATE-` で test-design に起こした)。依存: certificate (§2) の eligible 判定を draft PR 生成が使い、universal `harness-check` trigger (`ci-verification-contracts.md` §1) を accept が使う。

## 4. PLAN Admission の補足 (PLAN-L6-86)

`function-spec.md` の Admission 節に加えて次を契約とする。

- 駆動モデルの判定軸は遷移方向である。`reverse` は実装→設計 (実装事実を設計へ追従・正規化して Forward へ合流)、`redesign` は設計→実装 (監査・PoC 破棄・外部変化・上流判断を入力に設計を先に修正・差替え、合流後にその設計から実装する)。保存/廃棄は主軸ではないが矛盾状態を拒否する: reverse は `preserved`、redesign は `discarded` または `none` だけ許可。redesign は起点証拠・`supersedes` 対象・Forward 合流先・合流後に開始する実装 PLAN/revision を receipt へ束縛する。
- 書込順序と原子性: 全検証 Green 後に durable authoring journal へ intent を記録 → SQLite Unit of Work (ID 予約と PlanAsset/ledger append を未 commit) → その receipt から authoring source と tracked projection を生成 → 両成果物の temp write / fsync / rename 後に SQLite commit → journal を terminal へ。通常の拒否・失敗では PLAN file・reservation・ledger・projection・outbox を残さず、DB commit 前の例外は file restore と DB rollback の双方を検証し曖昧なら成功へ倒さない。強制終了時は journal 未完として fail-close し、次回起動・hook・CI が ledger receipt・preimage・postimage・temp/rollback file を照合して recovery か明示 rollback を終えるまで正本扱いしない。process 内 token を recovery 証拠にしない (path と digest は journal event へ永続化)。DB 先行・file 先行の二段書込みは禁止。`--force` は name collision 解決だけに限る。
- 改ざん防止: `plan draft` が唯一の正式入口。receipt v2 は path・plan_id・asset/revision・本文を含む canonical content digest・command_id・receipt digest を束縛し、tracked append-only projection として出力される。diff fence が Git base/head の PLAN と projection を照合し、手製 receipt・別 PLAN へのコピー・rename・本文だけの改竄を hook / pre-push / PR CI で拒否する。Issue webhook は signature・dedupe・enum・origin を検証し不正なものは quarantine して PLAN へ進めない。
- 実装状況: `src/plan-admission/` (draft service・atomic publisher・sqlite-draft-journal・diff-fence・tracked-receipt-*) に実装済みで、oracle は test-design の `U-PADM-001..011` へ昇格済み。残るのは所有 PLAN-L7-435 側の CLI/hook/CI oracle の確認記録である。
