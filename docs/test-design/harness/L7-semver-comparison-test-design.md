# semver 比較の置き換えのテスト設計 (issue #1721)

## 1. 対象と上位の契約

上位の契約は `docs/design/harness/L6-function-design/semver-comparison.md` の §4 (挙動の表) と §5 (食い違いの決定)。本書は、その表の各行を oracle の候補にする。置き換えは後続の Refactor PR が行い、各 PR の Red で候補を正式 ID (`U-SEMVER-*`) へ昇格する。それまでテストは引用しないので、すべて `CANDIDATE-` で宣言する (`src/lint/oracle-test-trace.ts` は `CANDIDATE-*` を宣言にも引用にも数えない)。 A の分 (001〜014・029・030) は昇格済みで、`tests/semver-comparison-a.test.ts` が引用する。B の分 (015〜021・031) も昇格済みで、`tests/semver-comparison-b.test.ts` が引用する。C の分 (022〜028・032・033) も昇格済みで、`tests/semver-comparison-c.test.ts` が引用する。

## 2. fixture

- 比較の関数は、値を渡すだけの純粋なテストにする。一時 dir も環境変数も使わない。
- `newestVersioned` は `existsSync` に依存する。一時 dir に空の file を作って「存在する候補」を作り、作らない path を「存在しない候補」にする。開発 repository の `.ut-tdd/`・`harness.db`・OneDrive を操作しない。
- A の関数は現在 module の外に出ていない。L6 §3.0 の契約に従い、`compareLenientVersion` (現在の `compareVersion` の改名) と `newestVersioned` を `src/runtime/adapter.ts` から export して直接呼ぶ。`parseVersion` は公開せず、`resolveClaudeNativeCommand` 経由の間接テストにもしない (0 と正が二値でしか見えず、符号を検証できないため)。
- 期待は、置き換え**前**の実装で先に通ることを確かめる (特性化テスト)。置き換え後も同じテストが通ることが、挙動を保った証拠になる。全件が置き換え前に通る。置き換えで意図して変える挙動は無い (契約 L6 §5)。

## 4. 昇格の手順

実装 PR ごとに、その PR が置き換える範囲の候補 (A は 001〜014、B は 015〜021、C は 022〜028 と 032、033。A の 029、030 と B の 031 は、それぞれの PR に含める) だけを正式 ID へ昇格する。Red は、置き換え前の実装で特性化テストが通ることと、置き換え後も通ることを確かめる。`tests/update-check.test.ts` の既存の `U-UPDCHK-001` `U-UPDCHK-002` `U-RELVER-002` `U-RELVER-003` は、引き続き通す。
