# R06 / 0.6.0：UT準拠BugBot

状態：版割当の提案・未実装/未受入。元M：M3b。構想target：v4.0。
責任：repair worker owner / independent reviewer。実名/代理/予算上限は正式採択時に設定。
関連移行：共通互換性規律。

## 1. 利用者がこの版で得るもの
再現可能な局所不具合を、共通契約の範囲内で修理し独立受入まで閉じる。

## 2. 新しく対応する範囲
- finding→dedupe→route/PLAN/V-pair→scheduler→再現→回帰test→限定修正→独立review→admission。
- 再現入力と期待動作を既存契約へ結び、修正前Red/修正後Greenを保存。
- 原因別のretry/部分工程回復、回数・時間・token・差分上限、no-progress停止。
- 安全/仕様/権限/支出/テスト期待値の自己緩和を拒否。正常修正と故障時回復を検証。

## 3. この版に入れないもの
- JSON/制御/安全受入前の仮設Bot。
- 要求が不明なのに期待値を発明、無制限retry、self-review/無承認merge。
- 全種類のバグ修正保証、プロダクト本番への自動デプロイ。

## 4. 何を入れ替え、何を残すか
| 旧方式 | 新方式 | 維持/境界 |
|---|---|---|
| チャットで手動診断と再委譲 | 共通findingからの限定修復worker | 既存routeとadmissionが統制主体 |
| 保存失敗も全reviewやり直し | 同一性確認後の未完了工程再開 | 捏造したreceiptで救済しない |

## 5. 着手と公開の条件

開発前提の成立と、consumerへ新capabilityを有効化できる条件は別。必要な先行schema/安全性だけを早期sliceにし、未受入のwriteを先に許可しない。

## 7. 有効化の順序
read-only→dry-run→低riskの一種類→対象scope拡大。自動mergeは初期既定off、導入先が事前許可した狭いscopeのみ後から有効化。

## 8. 移行失敗とrollback
repair capabilityをoffにし新規起動を止める。未mergeは履歴付きterminal、merge済み誤修正は新しい通常修正/revert契約で戻す。履歴消去やprotected branch forceはしない。

## 9. 旧経路をいつ止めるか
Bot独自parser/queue/receipt/権限は作らないので置換不要。手動修正入口は共通UTの正当なfallbackとして保持。

この版で先行sliceを始めるFR：既に開始した共通契約を継承。
開始と一式受入が別版のFRは、trace/REQUIREMENT_COVERAGE.mdの注記を参照。既存BR/FR/ACのIDとsourceは保持し、新しい架空のPASSを付けない。
