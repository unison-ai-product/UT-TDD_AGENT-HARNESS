# R03 / 0.3.0：共通JSON正本・契約API

状態：版割当の提案・未実装/未受入。元M：M2a。構想target：v4.0。
責任：record/authority責務owner / QA。実名/代理/予算上限は正式採択時に設定。
関連移行：MIG-02, MIG-03, MIG-04, MIG-06, MIG-07, MIG-08, MIG-09, MIG-10, MIG-11, MIG-12, MIG-13, MIG-14, MIG-16, MIG-19, MIG-20。

## 1. 利用者がこの版で得るもの
後続のCI・配布計画・BugBotが同じ機械契約と認可済みwriterを使える状態にする。

## 2. 新しく対応する範囲
- 要求/設計/ACのtyped参照、project/actor/decision/policy、finding/work item、verification、attempt/receipt、schedule入力を共通型で定義。
- canonical reader/validator、revision・CAS・idempotencyを持つ共通writer。DB/GitHubは再構築可能なprojection。
- 新規recordと既存形式を共通adapterで識別。移行対象ごとにauthoritative storeを一つに指定。
- 管理の権限変更は旧有効policyで認可。scope・委任・失効をrecordに持つ。
- scheduleの依存/資源/見積り根拠、contextのmodel/packet/対策参照を今から収録し、後付けschema乱立を避ける。
- 既存review/advisor/triage等の判断出力を共通judgement recordへ接続するadapterを対象inventoryに対応付け、record無しの新規admissionを拒否。未対応callerは明示して書込みを有効化しない。

## 3. この版に入れないもの
- 全Markdown本文/歴史PLANの一括JSON化。
- 能動配布・本番BugBot・MLによる順序最適化。schemaがあるだけで実行許可しない。

## 4. 何を入れ替え、何を残すか
| 旧方式 | 新方式 | 維持/境界 |
|---|---|---|
| 各consumerの独自prose抽出 | 共通typed参照とreader | narrativeはMarkdownで維持 |
| DB/GitHubとfileの二重編集 | 一つの正本writer＋再生成 | 旧readerは明示したlegacy recordだけに対応 |

## 7. 有効化の順序
旧record読取→read-only shadow→対象recordの移行→新規recordのwriter切替。未移行PLANのfrontmatterは旧正本、移行済みrecordだけJSON正本。

## 8. 移行失敗とrollback
切替前はshadowを破棄可能。切替後はwriter停止・イベント差分保存・逆変換互換性の確認が必要。対応不能ならread-only維持で旧writerへ無理に戻さない。

## 9. 旧経路をいつ止めるか
同一recordを読む独自parserを対象ごとに廃止。全歴史用readerはreadonly importとして残す。
