# UT-TDD 構想書 v4.0 L1 要求候補 (チーム開発版)

## Authority 境界

本書は PLAN-L1-09 の未承認候補である。current の L1 業務要求 (BR-01〜08 / BR-22 / UX-01〜03) ではない。
承認後は `docs/design/harness/L1-requirements/business-requirements.md` §1.2 へ未使用の番号で合流する。
合流した後、本書は候補から昇格記録へ役割を変える。

ただし、v4 の決定は current の BR-04 (PoC の契約化) と BR-05 (PLAN 単位のフェーズ管理) と衝突する
(V4D-054 Scrum / PoC 撤廃、V4D-078 PLAN 全面廃止)。昇格するときは、この 2 件を additive に残さず改訂する。

PLAN の廃止は v4 への切り替えのときに行う (V4D-078)。それまでは本書も PLAN-L1-09 を正規の受け皿とする。

## 決定台帳との関係

本書の各要求は、PO の決定を集めた決定台帳 `v4-decision-ledger.json` の決定 ID (V4D-xxx) を根拠に持つ。
有効な決定は、どれかの要求へ写るか、対象外の理由を持つ。この対応は次のコマンドで機械的に確かめる。

```bash
node scripts/v4-ledger-check.mjs
```

要求の書き方の規則 (V4D-087):

- 既存の要求と同じ論点の決定は、既存の行を直す。ID は変えない。
- 新しい ID を作るのは、どの既存の要求にも無い論点だけにする。
- 要求は「チームに何が要るか」を書く。作り方は要件と設計に書く。

## 期待する利用体験

人間は意図・要求・体験・承認境界・責務配分を示す。管理知能はチケットの下書きを作り、PO がまとめて発行する。
チームはチケットを取り、互いに独立した単位で並行して進める。ハーネスは検収を別の family で行い、同じ HEAD の証拠で閉じる。
衝突は担当区分と独立した切り方で事前に防ぎ、起きたら持ち主へ型付きで戻る。
右腕は実装後に設計との一致を確かめ、食い違いを設計か実装へ戻す。
知見はハーネスの改善と人間向けの digest の両方へ流れ、人間に日常的な進捗操作を求めない。

## 非要求

- PLAN を record 化して残すこと。PLAN は v4 で廃止し、既存分は凍結する (V4D-078)。
- Issue や DB を意味の正本にすること。
- harness.db をチームで共有する正本にすること (V4D-060)。
- 完全自動化 (human authority の AI への移譲)。
- provider 1 社構成での `cross_family` の僭称。同じ session 内の自己 review を独立 review として扱うこと。
- 参照元構想の全面移植 (repository / CLI の rename、多軸分類 registry による routeFiling の置換)。
- provider 固定の topology (provider 名を責務や authority の identity にしない)。
- Scrum / PoC (S0〜S4) を別の工程として持つこと (V4D-054)。
- 発注者 / 受託者の区別と、契約形態 (準委任 / 請負) の属性 (V4D-043)。
