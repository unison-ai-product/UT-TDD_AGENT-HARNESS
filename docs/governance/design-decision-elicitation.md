# 設計判断エリシテーション共通フォーマット (design-decision-elicitation)

Status: canonical
Created: 2026-07-13
Owner: PM / PO
Related: `CLAUDE.md` / `AGENTS.md` (コミュニケーション節)、`skills/design-decision-elicitation.md`

## 目的

AI ランタイム (Claude Code / Codex CLI) が PO へ設計判断を仰ぐときの聞き方を
1 つのフォーマットに固定する。対象は **設計判断のみ**:

- アーキテクチャ / 方式の選択 (trade-off が実在するもの)
- spec / AC の未確定点で、どちらに倒すかで成果物が変わるもの
- 既存 PO ルール・governance との衝突が疑われる場合の解釈確認

次は対象外 (このフォーマットで聞かない):

- 進捗確認・実行許可・「進めていいですか」類 (可逆作業は進める)
- コードや repo を読めば自力で確定できる事実
- 慣例的既定があるもの (既定を採って報告に書く)

## 共通ルール (両ランタイム)

1. 質問は **設計判断 1 件につき 1 問**、選択肢は 2〜4 個。
2. 各選択肢に **trade-off (得るもの / 失うもの)** を必ず書く。ラベルだけの選択肢は禁止。
3. **推奨案を必ず 1 つ決めて先頭に置き、「(推奨)」を付ける**。推奨理由を 1 行添える。
4. 判断材料が具体物 (コード断片・schema・UI 構成・ディレクトリ構成) で伝わる場合は
   preview (コードブロック / ASCII 図) を付ける。
5. 質問の前に **前提 (何を作っていて、なぜ今この判断が要るか) を 2〜3 行** で書く。
   PO が transcript を遡らずに答えられる自己完結性を保つ。
6. チャット出力なので日本語 (PO ルール 2026-06-22)。技術用語・PLAN ID・パスは原語のまま。
7. 回答を得たら、採択した選択肢と理由を PLAN の「設計判断」節 (または ADR) に記録する。
   チャット止まりにしない。

## Claude Code 側の実装

- AskUserQuestion ツールを **設計判断に限って** 使う (対話セッションのみ。
  非対話 / autonomous セッションでは使わず、最終報告に選択肢表を載せて次回入力を待つ)。
- `header` = 判断の種別 (例: "方式選択")、`question` = 前提込みの完結した質問文、
  各 option の `description` = trade-off、推奨案は先頭 + ラベル末尾に「(推奨)」。
- 具体物比較には `preview` を使う (single-select のみ)。
- 詳細な聞き方は `skills/design-decision-elicitation.md` に従う。

## Codex CLI 側の実装

Codex には構造化質問ツールが無いため、**同じ内容を markdown で出力して停止する**:

```markdown
## 設計判断依頼: <判断の種別>

前提: <2〜3 行>

| 案 | 内容 | 得るもの | 失うもの |
| --- | --- | --- | --- |
| A (推奨) | ... | ... | ... |
| B | ... | ... | ... |

推奨理由: <1 行>
```

- 表の後に必要なら preview 相当のコードブロックを添える。
- 出力後は実装を進めず PO の回答を待つ (設計判断が blocking の場合)。
  blocking でない部分は先行してよいが、判断待ちの旨を明記する。

## 逸脱の扱い

このフォーマットに乗らない設計質問 (選択肢なし・trade-off なし・推奨なし) は
review で指摘対象。フォーマット自体の改訂は本 doc を更新し、両ランタイムの
ルール節 (`CLAUDE.md` / `AGENTS.md`) と `skills/design-decision-elicitation.md`
を同時に揃える (rule-drift と同じ divergence 防止方針)。
