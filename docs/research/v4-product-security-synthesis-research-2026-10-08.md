# v4 補強: ハーネスで作る製品のセキュリティと停止対策

- 作成日: 2026-10-08。作成: security-audit (統合と照合のみ。repo と GitHub は変更していない)。
- 論点 (PO 指摘): 守る対象は**ハーネスを使って作る製品**である。漏えいや停止を起こさないために、ハーネスが V モデルの各工程で何を要求し、何を強制し、何を検証するかを決める。
- 入力: research-4 / research-4b (事案とガイダンス)、v4-reinforcement-synthesis (前回 §4)、v4 候補 3 文書 (`c:\dev\ut-v4-requirements-20261007\docs\governance\candidates\` の requests / requirements / acceptance)、`v4-roadmap/workstreams/03_SECURITY.md`、現行 repo のテンプレート。
- 出典の印: [確認] = 一次資料、または repo を直接見て確かめた事実。[二次] = 複数報道や集計記事による。[要確認] = 単独報道、記憶ベース、または未検証。
- 今回は WebSearch / WebFetch を使えなかった。事案の事実は材料レポートの範囲に限る。

## 結論 (10 行以内)

1. 2026-09 以降の国内事案の主な原因は 7 つあった。未パッチの公開機器、内部ツールの露出、委託先・保守アカウント、認証情報の管理不備、削除済みデータの残存、検知の遅れ、変更作業による停止である。CI のテストで防げた事案は少ない。多くは**設計 (露出面・認証情報・委託経路) と運用 (パッチ・検知・棚卸し)** の工程で防げた。
2. v4 の FR / AC 76 件はハーネス自身の統制に向いている。製品の保護を工程に結びつける FR は無い。FR-073 は「非機能の水準」を入力に使っているが、その定義はどこにも無い。FR-066 の L13 / L14 も「v3.1 から変えない」とだけ書いてあり、中身が無い。
3. 現行 repo には L4-security、L13、L14、DR、privacy の設計テンプレートがある。ただし `<記入>` が残っていても止める gate は src に無い。[確認] 書く場所はあるが、書いたことを機械が確かめていない。
4. 提案は新規 FR 2 本と、既存 FR 9 本の改訂である。新規は FR-077 (製品保護 profile と工程ごとの義務) と FR-078 (運用証跡の有効期限) の 2 本。
5. 要求の強さは profile で変える。軸はデータ区分・露出面・可用性の 3 つと、追加の印 4 つ。宣言した profile は schema record と構成の事実で照合し、宣言が低すぎれば止める。PII を扱わない社内ツールには DAST、ペネトレーションテスト、通知期限の runbook を課さない。
6. どちらの新規 FR も PII・認可・secret・本番に触れる。FR に追加する前に advisor (design) へ相談し、PO の承認を取る。

## §2 工程ごとにハーネスが製品へ要求するもの

観点は 3 つ。脆弱性診断 (どこに穴があるか) / SOC (入られたら何分で気づくか) / ホワイトハッカー (攻撃者ならどこから入るか)。

各行は「要求する成果物」「強制する gate」「検証するテスト・証跡」の 3 つで書く。最後の列は、その行を課す profile の段階 (§3.4。B = Baseline、S = Standard、H = High。印は §3.4 の flag)。

### 2.1 要求・要件 (L1〜L3)

| 要求する成果物 | gate | 検証 | 適用 |
|---|---|---|---|
| **製品保護 profile の宣言**。データ区分・露出面・可用性・flag を持つ (§3.4) | L3 の freeze 時に profile が無ければ deny | profile と事実の照合 (§3.4) | 全て |
| **データ資産・PII の棚卸し**。項目ごとの区分・保持期限・削除方式・保存先を持つ。schema record から生成する | PII を持つ項目に区分の無いものが 1 件でもあれば freeze を deny | 生成した棚卸し view と schema record の digest が一致する | S 以上 (B は「PII なし」の宣言だけ) |
| **セキュリティ要件と悪用ケース (misuse case)**。認証の強さ、高リスク操作 (ポイント交換・決済・権限変更) の再認証と上限、RTO / RPO、検知目標の時間 | 高リスク操作に悪用ケースの AC が無ければ deny | AC が L9 / L10 の AT 宣言へ降りている (FR-065) | S 以上。C10 対策 |
| **漏えい時の法定対応の要件**。個人情報保護委員会への速報・確報の期限と本人通知の判断者 | PII 区分があるのに要件が無ければ deny | runbook (L14) と対になっている | PII 印あり。期限は「速報は概ね 3〜5 日、確報は 30 日、不正目的なら 60 日」[要確認: 施行規則の条文は未確認] |

### 2.2 設計 (L4〜L6)

| 要求する成果物 | gate | 検証 | 適用 |
|---|---|---|---|
| **脅威モデル**。データフロー、信頼境界、STRIDE、対策の対応。L4-security テンプレートの第 5 章を使う | L4 の freeze 時に `<記入>` が残っていれば deny。脅威の行が対策 (設計 ID か AT ID) へ結びついていなければ deny | 非著者 family の review | B は 1 ページ (データフローと境界だけ)、S は STRIDE、H は STRIDE + 攻撃ツリー |
| **認可モデル**。role × 機能、role × 画面、tenant scope、object 単位の所有チェック。テンプレートの第 2〜4 章 | 表に空セルがあれば deny | L9 の負例テストを**この表から機械で生成する** (§2.4) | S 以上。多テナント印なら tenant 列が必須 |
| **露出面の台帳**。公開する endpoint・port・管理画面・BI・保守経路の一覧と、各々の認証方式 | 台帳に無い公開面を構成 (IaC / ルーティング) から検出したら deny | L13 の露出スキャン結果と台帳を突き合わせる | 露出面が internal 以上 |
| **secret 管理の設計**。置き場 (secret manager か環境)、ローテーション周期、漏えい時の失効手順、初期パスワードを使わないこと | 設計に置き場が無ければ deny | L7 の secret scan と L14 のローテーション証跡 | 全て (B は置き場と「repo に置かない」だけ) |
| **監査ログ・検知の設計**。記録するイベント (認証・権限変更・高リスク操作・管理操作・保守ログイン)、保持期間、改ざん検知、PII のマスク、alert と triage の owner | 区分が PII 以上なのに、管理操作と保守ログインのイベントが無ければ deny | L13 で検知ルールの発火試験 (§2.6) | S 以上 (B は「エラーログに secret と PII を出さない」だけ) |
| **委託先・保守経路の設計**。委託先ごとのアクセス範囲、MFA、短命の資格、踏み台、操作ログ | 委託印があるのに設計が無ければ deny | L14 のアカウント棚卸し証跡 | 委託印あり。C6 対策 |
| **可用性と縮退の設計**。外部依存ごとの timeout、再試行の上限、circuit breaker、止まったときの縮退動作 | 外部依存が台帳 (FR-074) にあるのに縮退の行が無ければ deny | L9 の障害注入テスト | 可用性が business 以上、または AI 依存印あり |
| **バックアップ・DR の設計**。RPO / RTO、本番の資格情報から分離したバックアップ、復元手順。optional の 035 テンプレートを使う | 状態を持つ製品に設計が無ければ deny | L14 の復元演習の証跡 | S 以上。C11 対策 |
| **L5 / L6 のセキュリティ仕様**。入力検証と出力エンコード、ファイルアップロード (型・サイズ・実行の防止・隔離した処理)、パスワードの保存方式 (argon2 か bcrypt)、session と cookie の属性、rate limit、物理削除の仕様 | 該当する機能があるのに仕様の行が無ければ deny | L7 / L9 の AT | アップロード印なら upload 節は必須。C2 / C5 / C8 対策 |

### 3.3 (c) 新規 FR (2 本に束ねる)

どの既存 FR にも「製品の保護水準を宣言し、工程ごとの義務へ落とす」論点と「時間で切れる運用証跡」の論点が無い。この 2 つだけを新規にする。

**UTV4-FR-077 製品保護 profile と工程ごとの義務 (仮)**

- 要件の文案: system は、製品ごとに保護 profile (データ区分・露出面・可用性・flag) を project record に持つ。同じ profile と同じ義務表の版からは、同じ義務の集合 (要る設計成果物・必須 AT・release 条件) と同じ digest が出る。義務の成果物が無い、または `<記入>` が残る層は freeze を deny する。profile が必須とする security の AT が未合格なら release を deny する。宣言した profile は事実 (schema record のデータ区分、構成から見つけた公開面、依存の登録簿の外部依存) で照合する。宣言が事実より低ければ fail-close する。profile を下げることと義務を「非適用」にすることは、理由付きの人間の decision record があるときだけ許す。scanner の抑止は 1 件ごとに理由・期限・承認者を持ち、期限切れは違反に戻る。
- 束ねるもの: §2.1〜§2.5 のすべて。FR-073 の「非機能の水準」の正本。
- 受入案 (release 必須 yes。基準 2・5):
  - (a) PII の列がある schema に D = none の profile を宣言する → deny。
  - (b) `<記入>` が残る L4-security で freeze する → deny。
  - (c) 期限切れの抑止がある → 違反として再び出る。
  - (d) 同じ profile から義務を 2 回生成する → digest が一致する。
  - (e) AI lane が profile を下げる → deny。
- 作らないもの:
  - 独自の scanner、SIEM、ペネトレーションのサービス。harness は証跡の形式 (重大度付きの violation の配列。SARIF や CycloneDX の形を参考にする) と期限だけを定める。ツールは製品側が選ぶ (V4D-096、03_SECURITY「有料 SaaS を必須にしない」)。
  - 義務表の DSL。義務表は 1 つの JSON にする。

**UTV4-FR-078 製品の運用証跡と有効期限 (仮)**

- 要件の文案: system は、L13 / L14 の運用証跡 (露出スキャン、検知の発火試験、脆弱性の照合、委託先・保守アカウントの棚卸し、secret のローテーション、復元演習、runbook 演習、保持期限の執行) を、型付きの記録として取り込む。各記録は、実施日時・実施者・対象 (環境と版)・結果・profile が決める有効期限を持つ。期限切れか未実施の証跡があれば、その製品の release を deny し、管理知能 (F5 / F7) がチケットの下書きを出す。証跡の本体は FR-006 に従い証跡ログに置き、参照する側は ID と digest だけを持つ。自己申告だけの証跡 (結果ファイルや測定値の無いもの) は受け付けない。
- 束ねるもの: §2.6 のすべて。FR-074 の定期再検査の結果の受け口。
- 受入案 (release 必須 yes。基準 4・5):
  - (a) 復元演習の証跡が期限切れのまま release する → deny。
  - (b) 結果の無い「棚卸し済み」の自己申告 → deny。
  - (c) KEV に載った脆弱性を照合で検出する → 即時のチケット下書きが出る。
- FR-077 と分ける理由: FR-077 は freeze やリリースというイベントで動く。FR-078 は時間の経過で動き (コードを変えなくても期限が切れる)、owner も運用 owner である (concept v4.0 の層の表では L13〜L14 の owner は「運用 owner 1 名」)。1 本にまとめると、イベントと時計の 2 つの発火条件が 1 要件に混ざり、受入が観測しにくくなる。1 本にしたい場合は FR-077 の末尾に「時間で切れる証跡」節を足す形で統合できる。

### 3.4 profile の仕組み (過剰な要求をしない)

軸は 3 つと flag 4 つ。段階は各軸の最大で決める。

| 軸 | 値 |
|---|---|
| D データ | none / internal / personal (PII) / sensitive (要配慮・決済・認証情報を預かる) |
| E 露出面 | local / internal network / internet |
| A 可用性 | best-effort / business (業務時間内) / continuous (SLO あり) |
| flag | upload (ファイルを受け取る) / tenant (多テナント) / vendor (委託先・保守アカウントあり) / ai (LLM などの外部 AI に依存) |

| 段階 | 決まり方 | 主な義務 |
|---|---|---|
| B Baseline | D ≤ internal かつ E ≤ internal かつ A = best-effort | secret scan、SCA と期限、軽量の SAST、SBOM、設定 baseline、1 ページの脅威モデル、secret の置き場。DAST・ペネトレーションテスト・監査ログの保持・通知の runbook は**課さない** |
| S Standard | D = personal、E = internet、A = business のどれか | B に加えて、STRIDE、認可モデルとそこから生成する負例、監査ログ設計、DAST、悪用ケース、バックアップと復元演習、残余リスクの受容、法定通知の runbook (PII のとき) |
| H High | D = sensitive、または A = continuous | S に加えて、ペネトレーションテスト、攻撃ツリー、短い脆弱性期限、署名と来歴、段階展開の演習 |

flag は段階と独立に義務を足す。upload → アップロード仕様と攻撃テスト。tenant → tenant 列と別 tenant の負例。vendor → 保守経路の設計と四半期の棚卸し。ai → 縮退設計と注入テスト。

宣言の自己申告を信用しない仕組み (FR-012 と FR-023 の「事実から導く」を踏襲):

- D は FR-046 の schema record の列区分の最大値と照合する。
- E は構成 (IaC、ルーティング、公開設定) から見つけた公開面と照合する。
- ai と vendor は FR-074 の登録簿と照合する。
- 宣言が導出値より低ければ fail-close する。上げるのはいつでもよい。下げるのは人間の decision record が要る (PII と本番に触れるので高影響境界)。

ハーネスの開発工程そのもの (チケット・review・merge) は profile で変えない (FR-033 の「人数で工程を変えない」と同じ考え方)。変わるのは義務の集合だけである。

## §4 別枠: ハーネス工程の不具合 (agent が gate を近道できる)

前回 §4 の S-1〜S-6 と R-1 / R-2 は、ハーネス自身を攻撃対象として扱っていた。本書の観点では、これらは「製品を守る gate を、agent (または author 側) が近道できる」というハーネス工程の不具合として扱う。前回の分類と要件案はそのまま有効で、優先度だけを下の観点で見直す。

| # | 近道の型 | 製品保護への影響 | 前回の対応 |
|---|---|---|---|
| H-1 | 受領 (receipt) をローカルで偽造・差し替えて merge する | 製品の security AT と review を全部迂回できる | S-1 (受領の完全性、ホスト側での最終強制) |
| H-2 | Issue・PR・依存の README などに混ぜた指示で、agent に権限操作をさせる | 製品の secret を持ち出す、gate の設定を変える | S-2 (信頼境界と最小権限) |
| H-3 | **抑止ファイル・閾値・profile を author の agent が書き換える** (ignore の追加、重大度の閾値の引き下げ、D を none にする) | gate を残したまま中身を空にできる | **新規の観点**。FR-077 の「抑止は理由・期限・承認者」「下げるのは人間の record」で塞ぐ。抑止ファイルと profile の path を、FR-005 の担当区分で author の書き込み範囲の外に置く |
| H-4 | AT のテストや oracle を実装 worker が書き換える | 認可の負例を弱めて通せる | 前回 §3 の FR-054 / FR-065 改訂 (oracle を書き込み区分の外に置く) |
| H-5 | ハーネスのログ・memory・受領に製品の secret や PII が混ざる | ハーネスが漏えいの経路になる | S-3、FR-019、FR-038 |
| H-6 | 配った hook・設定・テンプレートが改ざんされる | 製品側の gate が無効になる | S-4 / S-5 |
| H-7 | GitHub や provider の停止中に、review を偽装したまま merge する | 縮退中に製品の検証が抜ける | R-1 (縮退中の merge 禁止) |

H-3 は製品保護に直結する。前回の一覧に無い近道なので、FR-077 の受入 (c)(e) で必ず試す。
