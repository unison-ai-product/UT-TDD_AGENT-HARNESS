## 1. 全体の結論 (先に読む)

古典手法の多くは「人手が高い」ために廃れた。
LLM で安くなったのは次の 3 つ。

1. 文書や契約を書くこと。
2. 読み比べて差分を出すこと。
3. 並列に再実行すること。

安くなっていないものもある。

1. 正しい oracle (正解の基準) を決めること。
2. 独立性を作ること。

この 2 つを取り違えると、古典手法を「儀式」として再生してしまう。

v4 に効く優先順位は次の 6 つ。

| 順位 | 提案 | 元の手法 | 判定 |
|---|---|---|---|
| 1 | L8 の食い違いを 3 分類 (要件欠落 / 未意図機能 / 挙動差) し、FCA/PCA と NCR 処置の語彙で振り分ける | (e)(h)(j) | 採用 |
| 2 | 状態遷移表を 1 つ書き、契約・負例テスト・usage 統計の 3 つに使う | (a)(b)(g) | 採用 |
| 3 | ハーネス自身を DO-330 / ISO 26262-8 の語彙で分類する (どの gate が人間 review を代替するか) | (e) | 採用 |
| 4 | 独立性を 3 軸 (技術 / 管理 / 資源) で receipt に記録する | (d) | 比較候補 |
| 5 | 「曖昧さ検出」: 設計だけから別 family が L7 テストを書き、期待値の不一致を仕様欠陥として拾う | (i) | 採用 |
| 6 | review finding に欠陥分類を付け、calibration の入力にする | (c) | 採用 |

重要な負の知見。
cross-family review は N-version と同じ構造を持つ。
独立と見なせるのは「部分的」だけ。
2026 年の 2 本の追試がこれを裏づけた。
したがって v4 は「cross-family PASS = 独立検証」と書かず、決定的 oracle を主役に置くべき。

## 2. (a) Cleanroom ソフトウェア工学

### 核心
- 開発と検証を分ける。開発者は単体テストをしない。
- box structure で仕様を段階的に詳細化する。
  black box (外から見た振る舞い) → state box (内部状態) → clear box (手続き)。
  各段で「正しさの質問」を使い、検証をチームで読んで行う。
- テストは統計的 usage testing。
  利用の Markov 連鎖 (usage model) から確率的にテスト列を引く。
  不具合データから信頼度を認証 (certification) する。
  [確認] 要旨は Whittaker の学位論文と DTIC ADA275951 の要約と一致した。
  usage model は仕様から作る。連鎖の比較で停止基準も得られる。
  https://trace.tennessee.edu/utk_graddiss/11033
  https://apps.dtic.mil/sti/tr/pdf/ADA275951.pdf
- 出自は IBM の Mills らで、1980 年前後 [確認: 講義要約] [要確認]。
  Mills, Dyer, Linger, "Cleanroom Software Engineering", IEEE Software, 1987 [記憶]。

### 歴史的に失敗した点
- usage model を作る専門家の工数が大きかった。
- 「開発者が単体テストをしない」という文化的抵抗があった。
- 正しさの検証 (読んで証明する) が人に依存し、スケールしなかった。
- 実利用の頻度データが無い新規製品では usage model が空想になった。
  (以上は [記憶] と一般論。個別の導入失敗事例は [要追加調査])

### LLM 時代に安くなったもの
- usage model の素データがある。
  v4 は FR-038 で receipt・hook event・incident を corpus として持つ。
  ここから遷移確率を数えられる。
- box 展開の下書きは LLM が書ける。
- 「開発者がテストしない」は、LLM 作者には抵抗が無い。
  むしろ作者 family とテスト family を分ける規則 (v4 の方針) と相性が良い。

### 強化する FR/AC
- FR-065 / AC-078 (AT の事前宣言): usage model を AT の入力形式に加えられる。
- FR-024 (merge の 5〜10% 監査 sampling): 抜き取り率に統計的根拠を与えられる。
- FR-042 (calibration): 「正答率」の信頼区間を出す計算を共有できる。
- FR-066 の L10 (システムテスト) / L12 (受入)。

### 採用提案 (比較候補 → 一部採用)
1. 採用: 監査 sampling に「ゼロ欠陥の上限」を付ける。
   n 件抜き取って見逃し 0 件なら、95% 信頼で見逃し率は約 3/n 以下 ("rule of three" [記憶] [要確認])。
   FR-024 の 5〜10% は、この式で「何件見れば何を言えるか」を record に残す。
   実装は 1 日以内 (PoC)。
2. 比較候補: L10 に usage-weighted テスト選択を入れる。
   harness.db の hook_events から CLI コマンド遷移を数えて、重みにする。
   MVP (1〜2 sprint)。
3. 保留: 完全な box structure。LLM が書く box は検証されない限り飾りになる。
   L4〜L6 の 3 層 (外部仕様 / 状態 / 手続き) が既に box の 3 段に近いことの確認に留める。

### 反例
- usage model は「過去の使い方」を映す。新機能は重みゼロになる。
  新機能は決定的な負例で守り、統計は回帰側だけに使う。

## 3. (b) Design by Contract / Eiffel と contract-based testing

### 核心
- 各ルーチンに事前条件 (呼ぶ側の責任)、事後条件 (呼ばれる側の責任)、クラス不変条件を付ける。
- 契約は実行時に検査でき、テストの oracle になる。
- 派生側は事前条件を弱め、事後条件を強めてよい (Liskov の振る舞い的部分型)。
- 出典: Meyer, "Applying Design by Contract", IEEE Computer 25(10), 1992 [記憶]。

### 歴史的に失敗した点
- 契約を書く習慣が根付かなかった。Eiffel が小さい市場に留まった。
- 事後条件が弱い (「何も壊さない」まで書けない) frame 問題 [記憶]。
- 契約をコードから後付けすると、コードの鏡になり、検出力が無い。

### LLM 時代
- 契約を書く手間は消えた。
- 代わりに新しい危険が出た。LLM が実装から事後条件を書くと、実装の写しになる (循環)。
  agent 向け契約の研究も出始めた。
  Leoveanu-Condrei, DbC 風 neurosymbolic 層 (arXiv 2508.03665) [確認: 検索結果の要約のみ]。
  Bhardwaj, Agent Behavioral Contracts (arXiv 2602.22302) [確認: 要約のみ。単一著者 preprint。自己申告の数値は未追試]。
- TypeScript では zod / JSON Schema の境界検証と、assert 風の事前・事後条件が現実的。

### 強化する FR/AC
- FR-062 (言語中立の JSON Schema が境界の正本): 構造の契約。ここに「振る舞いの契約」を足す。
- FR-004 / AC-006 (チケットの「ゴールの検証と根拠コマンド」)。
- FR-067 (L8): as-built から抽出した契約と設計の契約を比べる。
- FR-065 (AT 宣言)。

### 採用提案 (採用)
1. 設計文書 (L6 の component 単位) に「事前 / 事後 / 不変条件」の節を置く。
   書くのは設計 owner。実装から逆算しない。
2. L7 のテスト設計は、各条件に 1 件以上のテストを対応づける。
   対応表は機械が生成する (FR-006 の構造化正本)。
3. L8 では、as-built から別 family が抽出した契約と、設計の契約を比べる。
   「実装が事後条件を弱めた」「事前条件を勝手に強めた」を型付きの食い違いにする。
4. 実行時の契約検査は、境界 (CLI 入力、Kernel の admission、言語間 JSON) にだけ入れる。内部全域には入れない。最小実装原則 (CLAUDE.md) に合わせる。

難易度: 設計文書の節追加は PoC。生成表と L8 比較は MVP。

### 反例
- 契約を LLM が設計文書の段階で書くと、設計の誤りも契約に固定される。
  契約の review も cross-family で行う。ここは FR-013 の範囲。

## 4. (c) Fagan inspection と形式的 review

### 核心
- Fagan, "Design and code inspections to reduce errors in program development",
  IBM Systems Journal 15(3), 1976 [記憶]。
- 役割: moderator (進行) / author / reader (言い換え担当) / inspector / scribe [記憶。流派で差あり]。
- 工程: planning → overview → preparation → inspection meeting → rework → follow-up。
- entry criteria (入場条件) と exit criteria (退場条件) がある。
- checklist を使い、欠陥を分類して数える。検査速度に上限がある。
- rework の確認は moderator が行う。

### 歴史的に失敗した点
- 会議の日程調整が重く、形骸化した。
- 会議自体の効果は薄いという研究がある (Votta, 1993 [記憶・要追加調査])。
- checklist が古くなる。速度上限が守られない。
- 欠陥数が人事評価に使われ、隠蔽が起きた [記憶]。
- 「合格を出すための review」になり、見逃しが残った。

### LLM 時代
- 会議は要らない。個別の準備 (preparation) を並列に回せる。
- 視点別 checklist (perspective-based) を複数 reviewer に割り当てるのが安い。
- 人事評価の副作用が無い (ただし LLM の「過検知」と「迎合」は別の歪み)。

### v4 への写像
| Fagan | v4 の相当物 |
|---|---|
| moderator | control plane。blind packet を組み、往復を管理する (FR-051 a, FR-050) |
| author | author family。claim は packet に入れない |
| reader (言い換え) | claim-blind lane。仕様 / AC だけから成果物を読み直す (FR-051 b) |
| inspector | spec-blind lane。成果物の内部整合を見る (FR-051 b) |
| scribe | judgement record (FR-041) |
| entry criteria | CI green、exact HEAD 束縛 (FR-013, FR-023) |
| exit criteria | blocking 0、軽作業の是正 3 回以内 (FR-031) |
| follow-up | 同じ非著者 reviewer の再検 |
| 欠陥分類・統計 | **v4 に未整備**。FR-042 の calibration 入力として足せる |
| 検査速度の上限 | **v4 に未整備**。packet の大きさの上限として足せる |

つまり v4 は Fagan の役割と退場条件をほぼ再発明している。
足りないのは「欠陥の分類」と「検査量の上限」の 2 点。

### 強化する FR/AC
- FR-013, FR-041, FR-042, FR-051 / AC-053, AC-063。
- FR-010 (トラブル記録 → パターン抽出): 分類があるとパターン抽出が機械的になる。

### 採用提案 (採用)
1. FINDING に分類軸を足す。最小は次の 4 つ。
   - 契約違反 (設計と食い違う)
   - 欠落 (要件 / 異常系が無い)
   - 余剰 (要求に無い機能)
   - 規約 / 品質
   これは (e) の双方向トレースの 3 分類と同じ語彙にそろえる。
2. judgement record に `defect_class` と `found_by_lane` (claim-blind / spec-blind) を足す。
   FR-042 は lane ごとの見逃し率を測れる。
3. packet に「diff 行数の上限」を置く。
   これは PR スコープ規律 (1 PR = 1 論点) と整合する。
   上限値は未確定。Fagan の速度表や Cisco 事例の数値は [要追加調査]。実測から決める。
4. 「FAIL を探す review」と「PASS を出す review」を分けない。
   反証試行 1 件以上 (FR-051 d) は Fagan の「欠陥を探せ」の LLM 版であり、良い設計。

難易度: PoC。

### 反例
- 分類が細かすぎると reviewer の負担になり、分類の質が落ちる。4 分類から始める。

## 5. (d) IEEE 1012 V&V と IV&V

### 核心
- IEEE 1012 は、ライフサイクルの各工程ごとに検証 (正しく作ったか) と妥当性確認 (正しい物を作ったか) の作業を定める。
- 整合性水準 (integrity level, 1〜4) が高いほど、必須の V&V 作業が増える。
  [確認: 水準 1〜4 と「高いほど厳格」は検索結果と一致。2016 版で対象がシステム・ハードに拡大。
  現行版の状態は要確認 (販売ページで 2024 版が策定中とあった)]
- IV&V は、V&V を開発組織から独立した組織が行う。
  独立の 3 軸は「技術 / 管理 / 資源 (財務)」と記憶している。
  [記憶・今回の検索では確認できず → 要追加調査。原文 (IEEE Xplore) で確認すること]
- NASA の IV&V プログラムは [記憶] 1990 年代に設置された [要確認]。
  NASA-STD-8739.8 と NPR 7150.2 が関連する [記憶・要追加調査]。

### 歴史的に失敗した点
- IV&V が工程の終わりに置かれ、遅すぎる指摘になった。
  効果は要件・設計段階の指摘で最大、という NASA 側の知見がある [記憶・要追加調査]。
- 独立が名目だけになった。同じ予算元・同じ前提で動くと、同じ盲点を持つ。
- 全部に適用して高コスト化した。
- 検証側が開発側の資料だけを読み、開発側の前提を引き継いだ。

### LLM 時代
- IV&V を全チケットに安く回せる。
- ただし「独立」を何で担保するかが、LLM では曖昧になった。
  別 family でも訓練データが似る。同 family の別 session は文脈だけが違う。
  これは (i) の問題と同じ。

### 強化する FR/AC
- FR-023 / AC-032, 033 (provider topology と evidence tier)。
- FR-024 (single-provider の補償統制)。
- FR-055 / AC-067 (L9 以上は author 以外の人間が review)。
- FR-056 の深度 profile (AC-068: risk 信号の record が要る)。

### 採用提案
1. 比較候補: 整合性水準をチケットに持たせる。
   水準 → 必須の review 深さと必須 AT を引く表を 1 つ持つ。
   v4 は既に「高影響境界」と「深度 profile」を別々に持つ。1 つの軸に統合できるかを検討する。
   これは新機構ではなく、既存 2 つの用語の整理。
2. 比較候補: 独立性を 1 つの tier ではなく 3 軸で receipt に記録する。
   - 技術: model / family / session / prompt pack が別か (FR-051 c, e が既に近い)。
   - 管理: author 側が verdict の採否を覆せないか。
   - 資源: reviewer の予算 (token / 上限) を author 側 lane が削れないか。FR-072 の費用記録と接続できる。
   既存の `cross_family / same_family_separated / intra_runtime` の 3 値は、この 3 軸の代表的な組み合わせとして残せる。
   難易度: MVP。「管理」「資源」軸は定義が曖昧なため、まず記録だけ。fail-close にはしない。
3. 保留: 人間による独立組織の IV&V。v4 の範囲外。

### 反例
- 軸を増やすと receipt の schema が重くなる。
  `evidence tier` が既に判定の入口として動いているなら、増やさない選択も妥当。
  採用の条件: 既存 tier で説明できない事故が実測で出たとき。

## 6. (e) DO-178C / ISO 26262 / IEC 61508: 双方向トレース、構造カバレッジ、ツール認定

### 6.1 双方向トレーサビリティ
- 要件 → 設計 → コード → テストを順方向にたどる (抜けた要件を見つける)。
- コード → 設計 → 要件を逆方向にたどる (未意図機能 = unintended function を見つける)。
- DO-178C は逆方向を明示的に要求する [記憶]。
- 構造カバレッジ (statement / decision / MC/DC) は、
  「要件ベースのテストが何を実行しなかったか」を測る完全性チェックであって、
  テストを作る方法ではない [記憶]。
- 失敗: トレース表が手作業で、古くなる。カバレッジを満たすためだけの、assert の無いテストが増える。

### 6.2 ツール認定 (これが v4 の核心に直結する)
ハーネスは「検証を自動化するツール」であり、人間の review を減らす根拠にも使われる。
航空・自動車の世界では、こういうツールに認定を要求する。

[確認] DO-330 / DO-178C のツール評価基準 3 種 (検索結果より)。
- 基準 1: 開発を自動化し、出力が機体ソフトに入る。誤りを混入しうる。
- 基準 2: 検証を自動化する。見逃しうる。出力が他の検証や開発作業の削減の根拠になる。
- 基準 3: 検証を自動化し見逃しうるが、他の作業の削減根拠にはならない。
- ソフトの DAL との組み合わせで TQL-1〜5 が決まる。TQL-1 が最も重い。
- DAL A: 基準 1 で TQL-1、基準 2 で TQL-4、基準 3 で TQL-5。
  この表は二次資料 (Rockwell Collins のスライド由来) であり、
  原典 (DO-330) で要確認。https://rapitasystems.com/do-330
- DO-330 では TQL-5 だけが主に black box で認定できる [確認: 二次資料]。

[確認] ISO 26262-8 第 11 章 (検索結果より)。
- ツール影響 TI (TI1: 誤り混入や見逃しが無い論拠あり / TI2: それ以外)。
- ツール誤り検出 TD (TD1 高 / TD2 中 / TD3 それ以外)。
- TI と TD から TCL を決める。2018 版は TCL1〜3 [二次資料。表そのものは未取得] [要確認]。
- 認定方法は 4 つ [記憶]。
  使用実績による信頼の増加、開発プロセスの評価、ツールの妥当性確認、規格に従った開発。
- 認定は「特定のプロジェクト・用途・版」ごと。
- IEC 61508-3 のツール分類 T1〜T3 [記憶・要追加調査]。

### v4 への写像
- v4 の gate は「基準 2」に当たるものが多い。
  例: FR-024 (補償統制)、FR-042 (LLM 判断を機械判断に昇格)、FR-051 (blind review)。
  これらは人間の確認を減らす根拠になる。
- v4 の AC (特に negative テスト、release-blocking = yes の行) は、
  実質的に「ツール妥当性確認のテストケース」になっている。
- FR-042 の calibration は、ISO 26262 の「使用実績による信頼の増加」を
  データで裏づける仕組みに相当する。
- 版の束縛: 認定は版ごと。v4 の receipt は candidate HEAD と CI generation を束縛する (FR-013) が、
  **検証した側のハーネス (gate の規則) の版**は明記されていない (本文を読んだ範囲では)。
  [要確認: FR-013 / FR-027 の他の箇所に書かれている可能性]

### 強化する FR/AC
- FR-013, 024, 042, 051, 054 (検収の条件を先に固める)。
- FR-046 / FR-064 (依存グラフ: トレースの自動化)。
- FR-067 / AC-080 (L8 の食い違い)。
- FR-065 / AC-078 (AT の事前宣言)。

### 採用提案 (採用)
1. **L8 の食い違いを 3 分類に固定する。**
   - A: 設計にあるが実装に無い (順方向の抜け)。
   - B: 実装にあるが設計に無い (逆方向 = 未意図機能)。
   - C: 両方にあるが挙動が違う。
   これに加えて「死んだコード / 無効化コード」を B の特別形として扱う。
   FR-067 の 3 つの行き先 (実装を直す / 設計へ backfill / 設計判断へ上げる) との対応は
   A → 実装を直す、B → backfill か削除、C → 3 つのどれか、となる。
   分類があると AC-080 の gate テストが書きやすい。難易度: PoC。
2. **gate ごとの「ツール影響」分類表を作る。**
   各 gate について次の 3 つを 1 行で記録する。
   - どの人間作業の代わりか。
   - 見逃したら何が起きるか。
   - 見逃しを別の手段が検出できるか。
   基準 2 に当たる gate には「独立 oracle」「mutation 検証」「calibration 実績」のどれかを必須にする。
   FR-024 の mutation 検証は既にこの方向にある。それを gate 全体の規則に一般化する。
   難易度: MVP。成果物は設計文書 1 本と gate 一覧の列追加。
3. **receipt に「検証者 (ハーネス) の版 digest」を束縛する。**
   gate の規則を変えたとき、古い PASS を新規則の証拠にしない。
   難易度: MVP。FR-013 の改訂になる。
4. **「カバレッジは完全性チェック」の原則を明文化する。**
   テストは要件 / 契約から作り、カバレッジはその後に測る。
   LLM はカバレッジを埋めるだけのテストを大量に書ける。
   だから mutation score (注入した欠陥を殺せたか) を、カバレッジの上位指標にする。
   MC/DC 自体の導入は保留 (TS の道具が弱く、過剰)。
5. トレース表は手書きにしない。FR-006 / FR-046 の構造化正本から生成する (すでに方針内)。

### 反例
- ツール認定は重い。航空では認定文書が数百ページになる。
  v4 は「分類 1 行 + 必須の検出手段」に留めること。
- 版ごとの再認定は、gate を頻繁に変えるチームを止める。
  変更の分類 (規則変更 / 実装修正) で再検証の範囲を決める。ここは (j) の Class I/II が使える。

## 7. (f) ATAM と ADR の系譜

### 核心
- ATAM (Architecture Tradeoff Analysis Method): SEI が開発した。
  品質特性の utility tree を作り、シナリオ (刺激 / 応答 / 尺度) で評価する。
  結果として「感度点 (sensitivity point)」「トレードオフ点」「リスク / 非リスク」を出す。
  文献: Kazman, Klein, Clements, CMU/SEI-2000-TR-004 [記憶]。
- ADR: Nygard, "Documenting Architecture Decisions", 2011 [記憶]。
  状態 (proposed / accepted / superseded)、文脈、決定、結果を短く残す。

### 歴史的に失敗した点
- ATAM は関係者を集める 2 日規模の workshop で、1 回やって棚に置かれた。
- ADR は書かれるが、更新されず、古い決定が残る (系譜が追えない)。
- 決定が検証可能な形 (測れる尺度) で書かれず、後から評価できない。

### LLM 時代
- utility tree とシナリオの下書きは LLM が速く作れる。
- 代替案の網羅と、決定間の矛盾検出が安い。

### v4 との関係
- FR-076: 設計判断は 8 原則のうち効く原則を 1 つ以上持つ。論点ごとに正本は 1 つ。
  既存論点は同じ ID で更新し、経緯は git で追う。
- これは「ADR を superseded の連鎖で積む」古典流とは逆方向。
  ただし v4 の決定台帳 (v4-decision-ledger.json) は `status` と `superseded_by` を持つ。
  つまり**系譜は台帳が持ち、本文は最新だけ**という役割分担で、整合している。
- 8 原則は品質特性の簡易版 (utility tree の上位ノード) として読める。

### 強化する FR/AC
- FR-076 / AC-089 (効く原則を 1 つも持たない記録の拒否)。
- FR-065 (AT の事前宣言): 決定ごとに受入シナリオを結ぶ。
- FR-066 (L4 ↔ L10): 設計の品質特性とシステムテストの対。

### 採用提案
1. 採用: 設計判断の record に「品質特性シナリオ」を 1 件以上入れる。
   形式は 刺激 / 環境 / 応答 / 尺度 の 4 項目。尺度は測れる値。
   効く原則の宣言だけでは検証できない。シナリオがあれば AT に落とせる。
   難易度: PoC (テンプレート 1 つ)。
2. 採用: 「感度点」を 1 行で書く。
   「この決定は X の前提に依存する」と書き、X が変わったら再検討の引き金にする。
   決定台帳の `maps_to` とは別の欄 (`depends_on_assumption`) になる。
3. 比較候補: ATAM 風のレビューを、L2 方式比較のときだけ軽量に行う。
   LLM が utility tree 案を出し、PO / 設計 owner が優先度を付ける。
   常設の工程にしない。FR-076 の「新しい ID は新論点だけ」を守る。
4. 保留: 全決定に ATAM。重すぎる。

### 反例
- 「最新だけ書く」規則は、台帳が壊れると系譜が失われる。
  台帳の改ざん検出 (hash 連鎖など) が要るかは [要追加調査]。

## 8. (g) モデルベーステストと property-based testing

### 核心
- MBT: 振る舞いのモデル (状態機械など) からテストを生成する。
  ISO/IEC/IEEE 29119-8 が MBT を扱う [記憶・要追加調査]。
- PBT: 例ではなく性質 (property) を書き、ランダム入力で検査し、失敗例を縮小する。
  QuickCheck: Claessen & Hughes, ICFP 2000 [記憶]。Python は Hypothesis、TypeScript は fast-check [記憶]。

### 歴史的に失敗した点
- MBT はモデル維持の費用がコードと同程度になり、モデルとコードが乖離した。
- モデルとコードを同じ人が同じ誤解で書くと、同じ誤りを共有する。
- PBT は「良い性質を考える」ことが難しく、自明な性質 (クラッシュしない) に偏った。

### LLM 時代
[確認] 検索結果より。
- Maaz ら (Anthropic / Northeastern): LLM agent が Python モジュールから性質を推測し、
  Hypothesis で検査し、偽陽性を落とす。100 パッケージで、報告の 56% が有効な欠陥、32% が報告に値する欠陥。
  上位 21 件では 86% が有効。ワークショップ論文 [要確認]。
- Property-Generated Solver (arXiv 2506.18315): PBT を LLM のコード改善ループの検証に使い、pass@1 が相対 23.1〜37.3% 向上と主張 [要確認]。
  著者の主張であり、未追試 [要追加調査]。
- LLM が書く性質は自明か誤りが多い、という報告がある (Vikram ら)。
  [二次資料 (survey) 経由のみ。原典未確認 → 要追加調査]
- 結論: 性質は安く書けるが、質は検証が要る。性質の出所が重要。
  **実装から作らせず、設計文書から作らせる**。

### v4 での適所
v4 には性質として書きやすい要件が多い。
- FR-003: owner はちょうど 1 (AC-004)。
- FR-002: RACI の A はちょうど 1 (AC-002 a)。
- FR-008 / AC-015: 同じ正本から 2 回 view を作ると byte 一致 (決定性)。
- FR-006 / AC-012: harness.db を消して正本から再構築しても同じ結果 (往復性)。
- FR-062 / AC-075: 同じ入力を TS と Python で処理して同じ結果 (differential)。
- FR-068: 右腕の順序を跳ばした遷移は deny (状態機械)。
- FR-058: provisional → frozen は人間の record だけ (状態機械)。
- FR-005 / AC-008: claim の二重取得は deny (状態機械)。

### 強化する FR/AC
- AC-002, 004, 008, 012, 015, 075, 081 の「negative テスト」群。
- FR-065 / AC-078 (AT の宣言)。
- FR-054 (検収の条件は先に固める)。

### 採用提案 (採用)
**状態遷移表を 1 つの JSON で書き、3 つに使う。**
1. 設計文書に、チケット / receipt / 凍結状態 / 右腕の工程の遷移表を JSON で置く。
2. 表に無い (状態, 事象) の組み合わせはすべて deny、という規則から負例テストを自動生成する。
   AC の「跳ばしたら deny」を手書きしなくてよい。
3. 同じ表に確率を付けたものが、(a) の usage model になる。
4. 事前 / 事後条件 (b) は、各遷移の guard と effect として書ける。

つまり、(a) (b) (g) は同じ表で済む。これが v4 を単純にする最も大きな提案。
難易度: 1 つの状態機械 (例: review request → receipt) で PoC。全体は MVP。
fast-check の stateful testing (`fc.commands`) が TS で使える [記憶・要確認]。

加えて次を採用する。
- PBT の性質は、設計文書の不変条件節から、author と別 family が書く。
- 性質の強度は mutation 検証で測る (FR-024 の mutation 検証に接続)。

### 反例
- 遷移表が設計の正本と食い違うと、表そのものが 2 つ目の正本になる。
  FR-076「二重管理しない」に反する。表は設計文書から生成するか、
  設計文書が表を指すだけにする。どちらにするかは決定が要る (比較候補)。
- 遷移表を持つ状態機械の数が多いと、メンテ費が出る。
  最初は gate に関わる 3〜4 個に限る。

## 9. (h) 文芸的プログラミング / spec-first / as-built

### 9.1 文芸的プログラミング
- Knuth, "Literate Programming", The Computer Journal 27(2), 1984 [記憶]。
- 説明文とコードを 1 つの源に書き、tangle (コード抽出) と weave (文書生成) で 2 つに分ける。
- 失敗: 道具への依存、大規模チームでの普及不足、文書とコードが同じ場所にあるため、
  コードの版管理と文章の版管理が絡んだ。
- 現在の形: Jupyter、org-babel、doctest、OpenAPI-first など。
- v4 への含意: 設計文書の中の宣言的な塊 (JSON Schema、遷移表、例) を抽出して
  テスト fixture に使う、という部分だけが再利用できる。

### 9.2 as-built (建設・土木)
- as-built 図面は、実際に施工された状態を記録する。設計図面からの変更を反映する。
- 近年は点群 (レーザースキャン) で実物を測り、設計モデル (BIM) と比べる。
  ISO 19650 が情報管理の枠組み [記憶・要追加調査]。
- 不適合 (NCR: nonconformance report) の処置は、典型的に次のとおり [記憶]。
  - そのまま使用 (use as-is。設計者の承認で例外を認める)。
  - 手直し / 修理。
  - 廃棄 / やり直し。
  ISO 9001:2015 の 8.7 (不適合なアウトプットの管理) が、
  是正、隔離、通知、特別採用 (concession) による受け入れを求める [記憶・要確認]。
- 重要な点: as-built は**実物を測って**作る。施工者の申告から作らない。
  測る人は設計者と別であることが多い。

### v4 との対応 (L8 の設計判断を補強する)
| 建設 | v4 L8 (FR-067) |
|---|---|
| 設計図面 | L4〜L6 の設計 |
| 施工物 | コード |
| as-built 図面 / 実測 | コードを正として作る as-built 仕様書 |
| 不適合の一覧 | 食い違いの一覧 |
| 手直し | 実装を直す (L7 へ) |
| 特別採用 (use as-is) | 設計へ backfill する (Reverse) |
| 設計変更・設計者判断 | 設計判断へ上げる |
| 検査員の承認 | 作者と別 family が振り分けを判定 (AC-080 c) |

v4 の 3 つの処置は、品質管理の古典的な不適合処置と一致している。
これは設計が正しい方向にあることの傍証になる。

### LLM 時代に安くなったもの
- 実測 = コードを読んで仕様を書くこと。人が行うと高かった。LLM は安く並列に行える。
- 設計と as-built の差分の一覧化も安い。

### 新しい危険
- LLM の as-built は、設計を知っていると**設計を写す**。
  実測者が設計者の図面を見て測ると、図面に合わせて数字を丸める問題と同じ。
- LLM は要約で細部を落とす。「そう書いてある」と「そう動く」は別。

### 強化する FR/AC
- FR-067 / AC-080 (L8 の gate)。
- FR-066 (L8 は L4〜L6 の設計全体と対)。
- FR-068 (右腕の順序: 証拠集め → 判定 → …)。

### 採用提案 (採用)
1. as-built を書く lane は設計文書を**見ない** (blind)。比較する lane だけが両方を見る。
   FR-051 の claim-blind / spec-blind と同じ構えを L8 に持ち込む。
2. as-built の各文には**根拠の位置** (file:line または関数名) を必須にする。
   根拠の無い文は食い違い候補にしない。
3. 重要な as-built 文は、特性化テスト (characterization test) に変えて実行する。
   「そう動く」を機械で確かめる。これは「コードを正とする」の実体化になる。
4. 食い違いの処置は 3 種のまま。上記 (e) の 3 分類と組み合わせる。
5. 許容差 (tolerance): 建設は許容差を設ける。
   v4 でも、表記ゆれのような意味の無い差を「食い違い」に数えない定義が要る。
   構造化フィールド (契約、状態遷移、スキーマ) を主な比較対象にし、散文は副次にする。
   これで AC-080 の「食い違い 0 件」が現実的になる。

難易度: 1 サブシステムで PoC。FR-068 の「最初の試行は 1 サブシステムで」と同じ範囲に収まる。

### 文芸的プログラミングの採用提案 (比較候補)
- 設計文書内の宣言的ブロック (id 付き) を抽出して fixture / schema の元にする案。
- 衝突: CLAUDE.md は「設計の契約文を PLAN へ複製しない。path と digest で指す」と定めている。
  FR-062 は product/contracts の JSON Schema を境界の正本とする。
  抽出方向が「設計文書 → product/contracts」か逆かで、正本が変わる。
  どちらかを正本に決める必要がある。決めずに両方へ書くと二重管理になる。
  → 設計判断が要る (advisor 相談の対象)。
- したがって、今は**保留**し、(g) の遷移表で同じ問題を先に決める。

## 10. (i) N-version programming と多様性 (Knight & Leveson の相関故障)

### 核心
- 同じ仕様から独立に N 個の版を作り、多数決で誤りを隠す。
- 前提は「版ごとの故障が独立」であること。

### Knight & Leveson (1986)
- 書誌: IEEE Transactions on Software Engineering, 12(1), 96-109 [確認]。
- 27 版を 2 大学で独立に作らせ、100 万件のテストをかけた [確認]。
- 個々の版は非常に信頼性が高かったが、複数版が同時に失敗した件数は独立の仮定より有意に多かった [確認]。
- 99% 信頼で独立性の仮定を棄却した [確認: 二次資料] [要確認]。
- 原因: 仕様のうち難しい部分で、別々の人が同じ誤りをする (難しさの関数が入力ごとに偏る)。
  Eckhardt & Lee (1985) の理論と整合する [記憶]。
- 反論と再反論があった [確認: 検索結果の要約]。結果は 1 つの問題への適用に限る、という注意もある。
- https://www.kth.se/social/files/564df871f2765419e306178d/KnightLeveson.pdf
- https://www.cs.washington.edu/homes/leveson/critics.pdf

### 2026 年の追試 (LLM) [確認: 本日 abstract を取得]
- Ron, Baudry, Monperrus, "N-Version Programming with Coding Agents", arXiv 2606.20158 (2026-06-18)。
  - Knight-Leveson の Launch Interceptor 仕様で再実験。agent 生成 48 実装、100 万入力。
  - **共通モード故障は大きかった。** 原因の多くは、仕様の難しい・曖昧な部分。
  - それでも 3 版の多数決で、平均失敗件数は 387.44 から 130.99 に減った。
  - 11,844 個の N-version の組が、失敗ゼロだった。
  - https://arxiv.org/abs/2606.20158
- Nogueira, Pattabiraman, Vieira, Campos, "A Systematic Methodology for Evaluating Failure Independence in LLM-Generated Code", arXiv 2607.02808 (2026-07-02)。
  - 224 問、12 モデル、5 言語、3 つの prompt 方式。
  - 同じモデルの実装は構造が似る。別モデルは構造が散る。
  - **別モデルでも、同じテストで一緒に失敗する頻度は独立の予測より高い。**
  - 3 版・5 版の合議で得られる信頼性向上は、独立の場合の約 0.43 / 0.44。同モデルの合議は 0.3 未満。
  - 失敗の型が違っても、根本原因を共有する例が多い。
  - https://arxiv.org/abs/2607.02808
- どちらも本日取得したのは abstract のみ。本文と手法の細部は未読。

### LLM-as-judge の自己選好 [要追加調査]
- 同 family を好む偏りの報告は多いが、今回確認できたのは二次資料 (blog) のみ。
  数値 (10〜25% など) は未検証。一次文献 (Wataoka ら 2024、"Preference Leakage" 2025) は未取得。
  採用判断に数値を使わないこと。

### v4 への含意 (重要)
1. v4 の「cross-family review」は N-version の構造と同じ。独立性は**部分的**にしか得られない。
   合議の利得は、独立なら得られる量の半分弱。
   それでも別 family は、同 family より明確に良い (0.3 未満 → 0.43)。
   v4 の方針 (hybrid を基準、single-provider は補償統制) は妥当。
2. だから「PASS = 正しい」と読ませない。決定的 oracle (テスト、型、schema、mutation) を主にし、
   LLM review は oracle が届かない所を補う、という順序を requirements に書く。
   FR-024 (補償統制)、FR-051 d (反証試行) はこの方向。
3. 共通故障は「仕様の難しい / 曖昧な部分」に集まる。
   これは、設計の曖昧さを見つける**探知器**に使える。

### 採用提案 (採用): 曖昧さ検出 (ambiguity probe)
1. 設計文書を凍結する前 (または L7 テスト設計の作成時) に、2 つの family が
   **設計文書だけから**独立に期待値付きテスト (または性質) を書く。
2. 期待値が食い違う箇所を、設計の曖昧さ候補として設計 owner に返す。
   返す先は FR-048 の backflow record。
3. 実装後は、2 family に同じ L7 を実装させ、back-to-back (同じ入力で出力を比べる) 差分を取る。
   差が出る箇所は、仕様の弱点か実装の弱点かを切り分ける。
4. これは「多数決で誤りを隠す」NVP ではなく、「不一致を欠陥検出に使う」使い方。
   NVP の本来の価値は、実はここにある (back-to-back testing)。
5. 費用: LLM では 2 回書かせるだけ。人手では高かった。
   高リスク (整合性水準が高い) の契約にだけ使う。全件には使わない。
6. 難易度: PoC (1 つの設計文書で試す)。
   成功条件: 凍結前に見つかった曖昧さの数と、実装後の Reverse 発生率の変化を測る (FR-042 に接続)。

### 反例
- 不一致が少ない = 曖昧でない、とは限らない (両 family が同じ誤読をする)。
  不一致ゼロは「検出できなかった」であり「曖昧さ無し」ではない。
- 実装版を複数持つと、保守費が倍になる。実装は 1 つにし、**テストだけ**複数 family で書く。
- 2 件の arXiv は新しく、追試が少ない [要追加調査]。

## 11. (j) 変更管理委員会 (CCB) と構成管理 (CM) baseline

### 核心
- CM: 構成項目を識別し、baseline を定め、変更を管理し、状態を記録し、監査する。
  標準: ISO/IEC/IEEE 828:2012 [記憶・要確認]。
- baseline: 承認済みの状態のスナップショット (機能 / 割当 / 製品の baseline など [記憶])。
  baseline 済みの項目は、変更要求 (ECR) を通さないと変えられない。
- CCB: 変更要求を評価する。影響分析、承認 / 却下 / 保留の処置、実装後の検証を行う。
- 監査: FCA (機能構成監査: 機能が要求どおり動くか) と PCA (物理構成監査: 製品が文書と一致するか) [記憶・要確認]。
- 変更の分類: Class I (形・適合・機能に影響。委員会が要る) と Class II (軽微。簡易処理) [記憶・要確認]。

### 歴史的に失敗した点
- CCB が会議体で、遅い。バイパス (影の変更) が生まれた。
- baseline が粗すぎる (全体を凍結する) か、細かすぎる (管理が追いつかない)。
- 影響分析が人の勘で、見落としが出た。
- 台帳と実体の乖離。

### LLM 時代
- 影響分析は依存グラフから機械で出せる。v4 は FR-046 と FR-064 で持つ。
- CCB の会議は、admission の機械処理と人間の承認 record (FR-001) に置き換わる。
- 影の変更は、path 区分の機械強制 (FR-005) と review 束縛 (FR-013) で防ぐ。

### v4 の決定台帳との比較
台帳の項目 (v4-decision-ledger.json の先頭を確認): `decision_id`, `source`, `date`, `summary_ja`, `status`,
`superseded_by`, `high_impact`, `maps_to`, `verified`。

| CCB / CM の要素 | 台帳での有無 | 所見 |
|---|---|---|
| 変更要求の識別 | あり (decision_id) | 同等 |
| 処置 (承認 / 却下 / 置換) | あり (status, superseded_by) | 同等 |
| 影響の大きさ | あり (high_impact) | Class I/II と近い |
| 要求への対応づけ | あり (maps_to) | 順方向トレースに相当 |
| 承認者の identity | **台帳の項目としては未確認** | FR-001 は別 identity を要求。台帳で見えるか要確認 |
| 影響分析の結果 (影響を受ける項目) | **なし** | FR-046 / FR-064 の出力を結べる |
| 対象 baseline | **なし** | frozen (FR-058) の単位と結べる |
| 実装の検証 (変更が実際に反映されたか) | `verified` が近いが意味未確認 | FCA/PCA に相当する監査欄が無い |

(台帳は先頭数件しか読んでいない。上の「なし」は全体の確認ではない。)

### 強化する FR/AC
- FR-058 (provisional / frozen)。frozen = baseline と読める。
- FR-048 (還流 record)。変更要求 ECR に相当する。
- FR-031 (軽い是正は同じチケット / 契約は戻す)。Class II / Class I に相当する。
- FR-029 (層ごとの owner)。baseline の管理者。
- FR-076 (決定の記録は 1 論点 1 正本)。

### 採用提案
1. 採用: 「frozen = baseline」を用語として明記し、frozen のものの変更は backflow record
   (= 変更要求) を通す、と一文で書く。新機構ではない。FR-058 と FR-048 の接続の明文化。
2. 採用: FR-031 の「軽い是正 / 契約の戻し」を、Class II / Class I の語彙で説明する。
   判定基準は既にある (上位契約を変えるか否か)。
3. 比較候補: 台帳に次の欄を足す。
   - `impact_set` (影響を受ける FR / AC / 設計 / path。依存グラフからの生成)。
   - `baseline_ref` (どの凍結単位か)。
   - `implementation_audit` (実装が決定に合致したか。L8 の結果へのリンク)。
   最後の欄は、L8 を「決定台帳の PCA」にする。
   台帳は「決めたこと」の記録から、「決めたことが実現したか」の記録にも広がる。
   難易度: MVP。
4. 比較候補: baseline の digest manifest (frozen 項目の hash 一覧)。
   CLAUDE.md の「設計系 PLAN は path + commit + sha256 で上流を指す」と同じ型。v4 では PLAN が無くなるため、
   チケット側の「上流の設計 revision digest」が baseline 参照になる。
5. 保留: 人間の CCB 会議体。PO / 設計 owner の承認 record (FR-001) で足りる。

### 反例
- baseline を細かく切るほど、変更要求が増える。FR-058 は「要求 / IR 単位」で freeze するとしており、粒度は妥当。
- 台帳へ欄を増やすと、FR-076「二重管理しない」と衝突しうる (影響集合は生成値であり、手書きにしない)。

## 13. 反対意見と衝突リスク (まとめ)

1. 儀式化の危険。
   古典手法の多くは、書類が目的になって死んだ。
   提案はいずれも「機械が生成・検査できる最小の欄」に絞った。
   機械が見ない欄は足さない (CLAUDE.md の最小実装原則)。
2. 既存ルールとの衝突。
   - 文芸的プログラミングの抽出は、設計文書の「複製しない」規則と衝突しうる (§9)。
   - 遷移表の置き場は、設計文書と product/contracts のどちらが正本かの判断を要する (§8)。
   - 台帳への欄追加は、FR-076「二重管理しない」と接する (§11)。生成値にして回避する。
3. 前提の弱さ。
   - 2026 年の N-version 追試 2 本は新しく、追試が少ない。
   - LLM が書く性質・契約の質を示す研究は初期段階。
   - 標準の表 (TQL、TCL) は二次資料から。原典未確認。
4. v4 側で本調査が読めていない範囲。
   FR/AC の本文の大半と台帳の大半。既に別の FR が同じ内容を持っている可能性がある。
   提案を設計へ入れる前に、重複を確認すること。
5. 今回の調査が扱っていないもの。
   IEC 61508 の詳細、MIL-STD の CM 規格の原文、NASA IV&V の実績データ。

## 14. UT-TDD フェーズへの対応と次の一手

| フェーズ | 使いどころ |
|---|---|
| L1 | 本書を材料として、v4 requirements の差分候補にする |
| L2 | 遷移表の置き場 (設計文書 / product/contracts)、独立性 3 軸の要否、台帳の欄追加を方式比較する |
| L3 | 採用分は受入条件 (AC) と ADR へ。L8 の 3 分類は AC-080 の再記述で反映できる |

推奨する順序。
1. PoC (1 日): L8 の 3 分類を AC-080 の文面へ反映する案を作る。
2. PoC (1 日): 監査 sampling の上限式と、FINDING の 4 分類を草案にする。
3. PoC: 1 つの設計文書で ambiguity probe を試す。
4. MVP: review request → receipt の遷移表から負例を自動生成する。
5. MVP: gate のツール影響分類と、ハーネス版 digest の束縛を設計する。
6. 設計判断依頼 (advisor 経由): 遷移表の正本の置き場、独立性 3 軸の採否。
   どちらも trade-off が実在する方式選択なので、PO へ上げる前に advisor 相談が要る (CLAUDE.md の規定)。
