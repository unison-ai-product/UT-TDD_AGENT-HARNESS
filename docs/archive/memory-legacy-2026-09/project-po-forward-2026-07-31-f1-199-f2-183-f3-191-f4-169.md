### F2 (#203) の方式は advisor 諮問で確定済み (独断でない)

`ut-tdd advisor --decision design` (provider=claude / `claude-fable-5`) に諮問し、
adversarial verify で **推奨 A / PO 裁定不要 (技術判断で可)**。Claude が持っていた前提 2 点が
**反証**された:

- 「A (gitignored 除外) は fence の検知力を弱める」は**誤り**。`captureGitWorkspaceFingerprint` は
  5 レーン構成で、git 系 4 レーン (`statusDigest` = `git status --porcelain`、
  `untrackedDigest` = `git ls-files --others --exclude-standard`、`worktreeDigest` / `indexDigest`
  = git diff) は **すでに gitignored を除外している** (`git-workspace-fingerprint.ts:83-118` を
  Claude 側でも実読して確認)。gitignored を hash しているのは `inventoryDigest` レーンだけで、
  これが設計上の outlier。A は「縮小」ではなく既存 git 意味論への整合。
- B (stat fingerprint) は**棄却**。EBUSY は消えるが、常駐プロセスが db/logs に触れるたび mtime が
  動くので **false positive が解消しない**。fence root は生きた worktree
  (`run-vitest-snapshot.ts:356` で `UT_TDD_TEST_FENCE_ROOT = repoRoot`) であり、3.4GB でなくとも
  テスト実行中に 1 byte 動けば violation になる。生成物除外は性能対策ではなく**健全性の必要条件**。
- C (明示除外リスト) は動くが allowlist 保守漏れで同型再発。D (サイズ閾値 skip) は
  「大きいほど見逃す」fail-open なので棄却。

**採用方式 A**: `captureWorkspaceInventory` の対象集合を `git ls-files -z` (tracked) +
`git ls-files --others --exclude-standard -z` (untracked 非 ignored) から導出する。
`git check-ignore` の逐次呼び出しは採らない (遅い / SSoT が既存レーンとずれる)。

**close 条件 (時間閾値テストは flaky なので採らない。除外の構造を assert する)**:

1. 負: temp fence root に `.gitignore` 記載の大ファイルと**排他ロック中のファイル**を置き、
   改修後の `captureWorkspaceInventory` の entries に現れず、例外も出ないこと。
2. 正: 非 ignored ファイルの追加 / 変更 / 削除が**引き続き** violation になること (両方向 fence)。
3. tracked なファイルが除外**されない**こと (`.ut-tdd/memory/` は git 追跡された正本)。
